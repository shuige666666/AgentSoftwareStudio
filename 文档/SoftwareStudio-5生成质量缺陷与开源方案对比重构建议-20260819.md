## 一、核心结论

当前生成质量问题有明确的工程原因：规划输出协议不充分，关键字段缺失后被错误默认值掩盖；固定脚手架仍由模型创建；多个规划结果重复拼进一个完整项目目标；新文件编辑协议要求模型传递不直观的 hash；历史按固定轮次压缩；开发、测试与修复之间的反馈距离较长。现有行为验收又不充分，因此“真实编译测试通过”仍不能代表用户需求已经实现。

这些问题支持改造生成链路，但不足以证明必须先建设完整规划编译器、符号依赖图、冻结执行清单和事件重放体系。更合理的方向是：先把模型应收到的信息交准确，让它从可构建骨架开始，以低摩擦工具连续完成实现、验证和修复；再根据实际失败引入业务里程碑、相关代码索引和恢复机制。

第一轮优先做四类事情：

- 修正规划的消息角色、字段 schema 和危险默认值，让模型更容易一次生成可用目标。
- 将 Spring Boot 固定工程骨架前移为平台脚手架，把模型预算留给业务代码。
- 改善编辑协议、Shell 执行、上下文和验证入口，提高每个模型轮次的有效工作量。
- 用需求一致的外部行为测试判断结果，并把真实失败反馈给同一开发循环。

任务拆分、RepoMap、双角色模型、诊断归并和恢复都可能有价值，但应按规模与失败类型逐步引入。模型能力和预算也是待测变量，不应在没有对照数据时排除，更不必等完整重构结束才开始观察。

这是一条允许结构性重构的路线，重点是替换低效的执行方式，而不是增加平台组件数量。判断改造是否值得，最终看相同需求下的行为结果、成本与完成时间。

### 2.3 正式范围

第一轮集中改善当前主要覆盖的 Java 17、Spring Boot、Maven 项目，优先使用已有 Profile 和模板。Web 页面、REST 与 WebSocket 的验收应按需求选择；现有贪吃蛇案例涉及 WebSocket，不能用 REST 检查替代。

纯 Java Maven、原生 Java 可以继续保留现有能力，质量结果按类型分别说明。第一轮不要求为所有类型同步建设新执行路径，也不因为暂未覆盖某类型就大规模增加产品状态体系。

第一轮沿用单次需求输入，不建设需求访谈和等待恢复接口。模型可以对未指定的普通设计细节形成显式假设；不能擅自增加 required 功能，也不能通过忽略核心要求宣称完整成功。

## 三、当前真实执行链

```text
用户需求
  -> PRD -> 初始化工作区
  -> 架构 -> 契约 -> 切片规划 -> 批次规划
  -> 一个 IMPLEMENT 会话实现全部生产代码
  -> 平台补齐部分 Profile 默认值，外层编译与修复
  -> 前端审查会话
  -> 测试生成会话
  -> 外层测试、契约检查与修复
  -> 持久化结果和报告
```

`SoftwareStudioWorkflowService.generateProjectWithResult()` 明确将切片用于上下文、预算和报告，不作为实际交付边界。`BatchGenerationService.generateProject()` 再将 PRD、文件结构、批次和契约的 toString() 一起拼入完整项目目标。

系统因此既支付多轮规划成本，又没有使用其分解结果来缩短反馈。另一方面，现有运行时已经能够循环调用工具、同步磁盘候选、记录停止原因，并将未完成产物交给外层验证。这些能力应继续复用。

当前问题不是“完全没有真实 Agent”或“完全没有质量判断”，而是目标表达、工具协议、预算分配和验证时机没有配合好。

## 四、缺陷、成因及对应改进

### 4.1 输出协议不足，不能只靠下游门禁补救

`ArchitectAgent` 没有明确要求返回 rootPackage，虽然目标 Java record 中存在该字段。`ContractAgent` 要求返回匹配 ProjectContract 的 JSON，却没有完整列出嵌套记录的准确字段结构。当前 JSON Mode 只声明 json_object，不提供完整字段 schema；Java 类名和本地 record 定义不会自动成为模型上下文。

`AbstractJsonAgent.askText()` 又把 SYSTEM 与 USER 拼为一个普通字符串。随后 Jackson 能解析的对象可能仍缺字段，`ApiEndpointContract` 和 `FrontendCallContract` 再将缺失 method/path 填为 GET 与 /，使缺失信息看起来已经合法。

优先修复真实 role、明确嵌套字段和必填要求、给出简洁有效示例，并在供应商支持时使用 schema 约束输出；不支持时仍发送准确 schema 并在本地校验。移除危险默认值后，对关键缺失给出字段级反馈。

确定性检查适合发现必填值缺失、路径非法和接口互相矛盾，但不能证明需求理解正确。rootPackage 可以在 mainClassName 为明确全限定名、且源码布局一致时确定性推导并记录来源；不必为可无歧义恢复的字段增加模型往返。

### 4.2 固定工程初始化占用模型预算

`ProjectProfileService.applySafeDefaults()` 已具备 POM 模板、依赖补充和最小 Spring 上下文测试能力，但主要发生在生产代码生成后。`BatchGenerationService` 仍要求模型创建 build configuration 和 application bootstrap。

应将 POM、入口类、基础配置、目录和启动性测试前移为确定性脚手架。它只需要可信的项目标识、包名和固定 Profile，不依赖完整符号图或全部业务文件规划。

脚手架的直接作用是减少样板生成与基础编译修复，不保证业务正确。contextLoads 仍仅作为启动检查，不能计入业务验收覆盖。

### 4.3 编辑协议与错误归因增加了无效往返

当前 apply_edits 已支持多文件数组，不是严格的一文件一调用。但它要求每文件一项、唯一 oldText 和精确 expectedHash，并把新文件创建也放进 hash 协议。实际轨迹已出现空 hash 导致的重复失败。

目标 patch 应明确表达 add/update/delete/move 和多处修改。创建文件只需明确“创建”的语义及路径是否已存在，不要求模型提供空文件 hash。更新文件根据上下文匹配；平台可以保留内部版本检查，发现陈旧读取时返回相关当前内容，减少整文件重读。

写入失败也不应恢复整个会话起始快照，丢掉此前成功工作。可先解析、校验本次补丁，再逐文件写入并准确返回已应用与失败部分；若选择回滚，只恢复本次操作涉及的改动。第一版无需追求通用跨文件事务框架。

### 4.4 上下文重复，压缩过早丢失工作过程

`WorkspaceAgentContextCompactor` 从第 6 轮后压缩，只保留最近 3 个模型轮次，却始终保留庞大的初始目标。短链接与投票历史目标分别约 17,686 和 26,835 字符，不能直接当成 token 数。

先精简输入：保留核心需求、对外接口、当前任务和必要代码，取消重复文件说明和批次 toString()。压缩按模型上下文预算触发，保留完整 assistant/tool 配对、已作出的关键决定、最近验证结果和未解决问题。

初期目录树、文件摘要、搜索和相关文件即可承担主要检索工作。完整语法图和 PageRank RepoMap 是后续选择，空仓库阶段不必再维护一套“预期符号图”。

### 4.5 执行与测试反馈分离，轮次不足的原因尚未完全识别

当前开发阶段禁止生成测试，随后另起测试会话；开发 prompt 又要求每组编辑后编译。多个尚未闭合文件的中间态可能产生重复编译成本，而业务错误发现偏晚。

应允许同一开发循环为当前功能编写局部测试、执行验证并据结果继续修改。平台维护的外部验收独立保留。针对还未形成完整单元的编辑，不机械要求逐次编译。

八个会话都达到轮次上限，说明上限真实约束了执行，但无法单独证明任务必须拆分，也无法排除模型能力或额度不足。应观察最后若干轮是否持续产生有效代码和验证进展，再决定调整预算、上下文或任务大小。

### 4.6 现有测试不充分，新增验收也必须与需求一致

`BenchmarkQualityEvaluator` 主要检查 placeholder、测试源码、测试绿色、SpringBootTest 和契约结果。只有 contextLoads 的项目可能满足多项结构指标，但尚未证明核心功能。

短链接基准原文要求生成、访问、查询信息、处理无效链接和必要测试，没有明确要求相同 URL 复用短码、访问计数或链接过期。不能把这些附加行为直接列为 required。若要考察它们，应发布明确的新案例版本，并让所有对照使用相同需求。

接口路径和字段未指定时，应先确定公开接口约定，再让外部测试按该约定调用。接口约定本身仍需对照用户故事，不能将生成契约自动视为正确需求。

固定基准可人工维护行为测试。任意用户需求的自动验收仍是能力边界：独立模型提前生成测试可以辅助，但不保证判卷正确。测试通过报告应写清已验证行为；未覆盖的重要要求不能悄悄从成功定义中消失。

### 4.7 修复进度不应要求错误集合每轮单调下降

`RepairProgressEvaluator` 主要比较阶段分数和问题数量，`ToolDrivenRepairService` 在一次 NO_PROGRESS 或 REGRESSED 后停止并回滚。这可能放弃有价值的中间修改。

修复一个公共类型后，编译器可能暴露新错误；错误位置移动，也不一定代表新的根因。诊断首先应服务于定位和下一步修复，不必一开始为每种错误建立复杂 owner 路由。

优先返回真实命令、退出码、首批关键错误、相关代码、最近 diff 和已通过行为。明确破坏已通过功能时恢复较好候选；若仅无法证明进步，可在剩余预算内允许有限继续探索。保留最佳可验证候选，与允许当前工作候选暂时不完整，并不矛盾。

### 4.8 模型和预算应作为早期可观察变量

工具请求当前固定 parallel_tool_calls=false，历史也确实一轮一调用，但只打开并行开关不保证更好。可先支持一次调用内合理批量操作，并依据模型能力处理多个独立调用；第一版写入仍串行。

更强模型可能更好地使用工具、理解错误或完成规划；更多预算也可能让接近完成的任务成功。它们都需要对照验证，而不是预先接受或排除。模型替换实验可以从基线开始，复杂多模型路由则无需提前建设。

## 五、四个开源项目的源码比较

### 5.1 mini-SWE-agent：优先学习简单执行循环

`agents/default.py` 的核心是 query、execute_actions 和下一轮观察，run 的 finally 中保存轨迹；环境接口负责执行。`environments/docker.py` 展示了持续存在的容器与 docker exec 调用，配置支持 Shell 组合命令。

值得移植的是模型/环境分离、简洁循环、每步保存证据，以及直接使用执行输出继续修复。其 SWE-bench 配置有任务特定约束和预算，不能据此给本项目套用固定轮次数，也不能把默认 Docker 参数视为完整隔离。

本项目的绿地脚手架和业务拆分属于额外适配，不能说成来自 mini-SWE-agent 的现成方案。

### 5.2 Codex CLI：借鉴 patch 和工具运行边界

`apply-patch` 提供明确补丁语法和多文件变更表达；`tools/parallel.rs` 根据工具并发声明取得读锁或独占锁；运行时还提供输出控制、停止与记录机制。

优先借鉴补丁语义、执行结果反馈和环境边界。Java 实现需裁剪并测试，不应为了复用 patch 一并移植通用产品架构。

当前快照的 `turn_diff_tracker.rs` 明确跟踪已提交 apply_patch 变更，不是任意 Bash 写入的通用文件发现器。目标系统仍需扫描或比较实际工作树，且不能把“复制此组件”写成已经解决 Shell 变更跟踪。

### 5.3 Aider：相关代码和可纠正的编辑反馈

`repomap.py` 使用定义/引用图及 PageRank 在 token 预算内选择上下文；`editblock_coder.py` 提供 dry-run、匹配失败反馈和部分应用结果；`base_coder.py` 可将 lint/test 错误返回后续轮次。

优先借鉴当前文件与其他仓库信息分开提供，以及编辑失败后指出具体失败块。完整 RepoMap 在较大项目中更值得验证，第一轮可以先用轻量文件索引。

`architect_coder.py` 的 architect/editor 是可选模式，editor 接收规划文本并选择编辑格式，不是通用的强 schema 业务调度框架。当前 auto_test 默认关闭，测试反馈依赖配置；文档中的“可以借鉴测试闭环”不等于它默认执行所有测试。

### 5.4 OpenCodeReview：完成记录有价值，冻结执行计划需谨慎

`session/manifest.go` 冻结被选中的审查文件集合，以 completed、reused、failed、waived 等覆盖集合计算结果；`llmloop/compression.go` 用 token 阈值压缩并保留完整轮次。

应借鉴明确完成状态、失败原因和按 token 管理历史。其待审查文件在执行前已确定，而生成项目的内部实现会演进；不宜将其 sealed selected set 直接改成“全部文件、符号和实现步骤一经规划即不可调整”。

初期执行记录只需说明任务、状态、当前工作版本和最近验证。跨 run 复用、waiver、identity lineage 与完整事件重放，在确有恢复需求时再引入。

### 5.5 复用优先级

| 机制 | 建议 | 预期作用 |
|---|---|---|
| mini-SWE-agent 简洁循环、环境接口 | 优先借鉴 | 减少角色交接，缩短行动与反馈距离 |
| Codex patch 协议、有界输出 | 优先借鉴并裁剪 | 降低编辑失败和无效往返 |
| Aider 编辑失败反馈、相关文件上下文 | 优先借鉴 | 让下一次尝试获得足够信息 |
| OpenCodeReview token 压缩和明确停止状态 | 优先借鉴简化版本 | 控制上下文与记录真实停止原因 |
| 完整 RepoMap、双模型角色 | 按效果实验 | 可能改善复杂任务，也可能增加成本 |
| 完整 Manifest、跨 run 恢复与事件重放 | 后续按需 | 提高可恢复性，不直接提高编码能力 |

## 六、改造原则与边界

本次重构的首要目标是提升最终生成项目的代码质量：功能符合需求、实现完整、逻辑正确、跨文件和前后端一致、能够构建运行，并具有与项目规模相称的可维护性。开发中的取舍先看生成代码是否更好，再看增加的平台复杂度和成本是否值得；不能为了减少工具调用、缩短运行时间或简化平台，牺牲必要功能、验证和修复。

脚手架、规划、工具、上下文和修复改造都是服务于这一目标的手段，其质量收益仍需真实产物验证。调用减少、运行加快、日志完善或平台更严谨，只能作为辅助证据；如果生成代码质量没有改善，就不能据此宣称重构目标达成。仅增加管理复杂度、又未帮助生成质量的设计应降低优先级或撤回；必要的执行隔离、持久化和验证可信性仍作为基础能力保留。

平台负责工作区、预算、工具执行、可信验证和结果记录；Agent 负责提出并实施代码变更。最终成功来自实际验证，不能由模型自述决定。

稳定的是用户要求、公开接口约定与基准判卷口径；内部文件布局、方法和任务拆分允许调整。发现计划错误时应反馈、修正和重新验证受影响行为，不能靠冻结错误计划维持表面一致。

首轮只对会破坏执行或结果可信性的实际问题设置阻断：关键目标无法确定、构建失败、明确 required 行为未通过。风格、可选功能、未知覆盖和普通建议分别报告。检查数量本身不是质量指标。

诊断、日志、缓存、快照和内部状态是支撑能力，不应各自变成额外关卡。基础设施异常仍可能终止执行，但不能被误记成代码语义错误。

## 七、推荐目标架构

### 7.1 一条简单主链

```text
用户需求
  -> PlanningAgent：需求整理 -> 总体设计与公开接口约定
  -> 关键字段校验/明确缺失的定向修复
  -> 平台生成可构建骨架
  -> DevelopmentAgent：开发循环
       读取/搜索 -> 修改 -> 平台验证 -> 获得失败反馈 -> 继续修改
       小项目可在一个连续会话完成
       大项目按业务能力逐步推进
  -> 最终需求行为验收
  -> Windows 项目代码与结果报告
```

实现初期复用现有 WorkflowData 和结果模型，不必一次新增六个中间模型。必要的新结构可以先限于脚手架输入、当前任务说明和验证反馈。

#### 7.1.1 默认两个模型角色，平台承担执行管理

目标主链固定为统一规划角色 PlanningAgent 和统一开发角色 DevelopmentAgent。这里的角色是职责和上下文边界，不代表必须使用两个模型，也不代表只能调用两次模型。第一轮沿用已有模型配置，不因角色重构强制引入多供应商路由。

| 角色/组件 | 负责什么 | 输入与输出 | 权限和完成边界 |
|---|---|---|---|
| PlanningAgent | 整理需求、总体设计、公开接口、必要业务任务建议 | 原始需求与平台 Profile；输出需求摘要和设计约定 | 不写生成源码、不执行 Shell、不修改外部判卷要求；平台检查关键字段后交给开发 |
| DevelopmentAgent | 实现后端与前端、编写开发测试、联调、阅读失败并修复、检查源码质量 | 原始需求、有效规划、真实工作区与验证反馈；产出磁盘改动和验证请求 | 可修改当前项目的生产代码和开发测试；不能修改平台验收资产或自行设置成功 |
| 平台服务 | 脚手架、工具执行、依赖准备、验证、状态同步和结果保存 | 接收结构化规划和工具请求；返回真实结果 | 决定当前代码版本和验证状态，不通过增加“管理 Agent”执行确定性工作 |

规划角色合并的是职责归属，开发角色合并的是编码责任和工作上下文。测试设计、前端联调和修复仍要做，只是不再默认分配给相互失去上下文的独立会话。

#### 7.1.2 PlanningAgent 的两步输出

第一版默认由同一规划角色分两次模型调用完成规划。第一步形成需求摘要，第二步基于原始需求和该摘要形成总体设计与公开接口；不强迫一次回复生成全部结构。简单项目是否合并为一次调用，后续通过对照决定。

需求摘要包含项目目标、具有稳定标识的用户行为、明确技术限制、合理假设和未解决问题。保留原始需求，避免只传 PRD 后逐层丢失用户要求。不得以“MVP”或“范围可控”为理由删除用户明确功能；可选建议与必需行为分开记录。

设计输出包含项目包名/入口、平台 Profile、关键领域职责、外部接口或页面交互，以及实现建议。HTTP 接口明确 method、path、输入字段、输出字段与必要错误语义；WebSocket 和页面项目使用对应协议/交互约定，不强制套成 REST。每个必需行为应说明由哪些可观察接口或交互实现，但不要求预测全部内部类、方法和文件。

首版可以复用 PrdDocument、ProjectStructure 和 ProjectContract 作为内部适配结构，新增字段只围绕上述实际需要。对模型暴露的 schema 必须完整且无歧义，不照搬冗长对象 toString()。设计步骤合并原架构和契约职责，避免两者反复重述、各自修改接口。

缺失字段反馈给产生它的步骤；可以确定性推导的值由平台补全并说明来源。基础依赖预取和脚手架渲染属于平台动作，不再调用规划模型确认普通文件操作。

#### 7.1.3 DevelopmentAgent 的工作协议

开发会话从已生成的骨架开始，默认持续负责完整项目。system 消息规定工具、质量要求与修改边界；任务消息提供原始需求、精简规划、当前能力和已知限制；工具消息提供真实操作与验证结果。不会将规划角色的全部讨论原样附加到开发历史。

开发顺序是理解现有骨架、实现一个可验证单元、补相应开发测试、提交验证、根据反馈继续。前端任务包含端点、载荷、DOM/模板变量与错误状态检查；纯后端任务不额外创建前端。收尾时对照必需行为和第 10.4 节检查明显源码缺陷，不新增强制的独立“质量 Agent”。

普通编译错误、测试失败和前后端不一致都由当前开发会话处理，不因为错误类别改变就重新分配角色。开发测试可修改，但应依据需求和失败证据纠正断言，不能删除有效测试或弱化正确断言以制造通过；平台外部验收始终不可写。

引入业务里程碑后优先在同一会话推进。上下文确实过大时可建立续接会话，传入当前代码版本、有效规划、已完成能力、关键决定与最新失败。续接仍是 DevelopmentAgent，不能把摘要当成已经验证的事实，必要时读取磁盘和验证记录确认。进程中断后的恢复在阶段三补齐最近 checkpoint 支持后再提供，首版先保证产物和日志可保留，不承诺自动恢复。

#### 7.1.4 规划调整、故障与控制权

类名、私有方法、文件拆合和其他不改变公开行为的调整，由 DevelopmentAgent 直接实施。普通代码缺陷不回到规划角色。发现实际需求与公开契约冲突时，开发者通过 report_blocker 的 planning_conflict 类别提交冲突、需求依据和建议，不直接更改判卷资产。

平台收到 planning_conflict 后暂停当前开发循环，定向调用 PlanningAgent 审查冲突；这是本次 run 内可恢复的交接，不等于立即将整个 run 判失败。保留现有源码，返回有效决定后续接开发，不重新生成骨架。拒绝无依据的变更时也应把原因反馈给开发，让其继续按现有约定实现。

基准需求和公开接口约定在一次对照中保持不变，规划角色不能为让候选通过而修改它们；确需修正基准时，另建案例版本并重新对照。普通生成中，用户指定的接口不可自行改；规划阶段自行选择的接口确有缺陷时，可以形成新版本约定并重验受影响行为。独立验收的预期不能直接依据当前代码反向修改。

未知模型或运行时异常保留候选和原因，平台按已有重试策略处理；环境问题优先交平台处置，不让开发 Agent 通过修改业务代码修网络。普通 task_blocked 表示无法继续，由平台记录未完成原因。重复交接不能无限循环，沿用 run 级停止策略即可，不新增复杂角色协商框架。

#### 7.1.5 旧角色和执行模式的去向

| 当前入口/模式 | 目标安排 | 需要保留的有效职责 |
|---|---|---|
| ProductManagerAgent | 并入 PlanningAgent 需求步骤 | 原始要求、用户行为与合理假设整理 |
| ArchitectAgent + ContractAgent | 并入 PlanningAgent 设计步骤 | 工程类型、关键设计、公开接口与前后端约定 |
| SlicePlanningService + BatchPlanningService | 单一业务任务建议/推进逻辑；阶段三按需执行 | 用户能力的依赖顺序，不新增规划角色 |
| IMPLEMENT | DevelopmentAgent 默认开发循环 | 生产代码实现，同时允许开发测试 |
| FRONTEND_INTEGRATION / FrontendReviewNodeService | 有 UI 时融入开发任务与收尾检查 | 接口、页面、脚本和错误展示一致性 |
| TEST / TestGenerationNodeService | 融入开发循环，取消仅能写测试目录的模式隔离 | 有意义的测试与真实执行反馈 |
| REPAIR_IMPLEMENTATION / REPAIR_TEST / REPAIR_CONTRACT | 作为开发会话收到的失败类型，不再各自开启默认角色 | 真实错误定位与修复 |
| ToolDrivenRepairService 等外围控制 | 逐步收敛为平台验证、候选保留与停止控制 | 防止回归、保留证据，不另起完整修复链 |

当前独立 Java Agent 类与工具运行时 mode 不是同一概念；上表同时处理两者，避免只合并类名却继续按原模式重启会话。迁移期间可保留旧 DTO、事件名和适配入口，但新主链不能依次执行新旧两套逻辑。

#### 7.1.6 可选审查角色与双模型实验

首版不默认加入独立 Reviewer。若真实产物反复出现开发者自检遗漏，可增加只读审查步骤，读取需求、源码及验证结果，输出带文件依据和影响说明的 findings，再由 DevelopmentAgent 修正。审查意见不自动成为新需求，也不能凭一句“通过”代替平台验收。

Aider 式 Planner/Editor 分离特指开发过程中“提出具体变更”和“按格式编辑”的分工，与项目开始时的 PlanningAgent 不同。只有复杂修改确有收益时才尝试；首版开发者自己完成两项工作。可选角色的加入按生成质量结果决定，不以角色数量作为架构目标。

### 7.2 规划与脚手架

规划输出包含用户需要的功能、关键接口和必要技术限制。文件蓝图是实现建议，可随业务编辑更新；不预先要求所有符号和引用闭合。

`ProjectScaffoldSpec` 仅表达项目标识、包名、入口类、固定 Profile 和本次需要的基础依赖。`ProjectScaffoldService` 复用已有 POM 模板，生成入口、配置、目录、.gitignore 和最小启动测试。Bootstrap 的编译证明骨架可构建，启动测试则在适当时执行；两者不能混称。

使用少量版本化本地模板，不要求每次在线调用 Initializr。只在新工作区生成骨架；业务编辑开始后，不再整模板覆盖。允许 Agent 在受控依赖来源内提出或实现必要构建调整，不能为了保护脚手架而禁止合理业务依赖。

### 7.3 模型可见工具

建议使用以下基础接口；工具数是接口设计结果，不是优化验收目标：

```text
bash(command, cwd, timeout)
apply_patch(patch)
submit_checkpoint(summary, scope = "progress")
report_blocker(reason, kind = "task_blocked")
```

bash 负责搜索、读取、组合命令与局部自诊断。apply_patch 表达源码改动，平台负责路径边界、匹配与实际写入结果。允许完整 Bash 意味着它也能写文件，工作区状态不能只跟踪 patch。

submit_checkpoint 初期就可作为正式验证入口，无需先实现 MilestoneGraph 或 sealed Manifest。第一版以整个当前项目的编译和全量已有测试为主，返回实际结果，不建设按任务自动选择局部检查的机制。后续可选 milestoneId 用于关联任务进度，不用于缩小正式验证范围。

scope 取 progress 或 final，主要区别是是否请求完成交付，而不是选择两套局部测试范围。progress 对整个当前项目执行编译和全量已有测试，结果返回后继续开发；通过只表示当前代码通过这些检查，不表示所有业务已实现。final 在此基础上执行项目既定的整体收尾验收，未通过则继续修复，通过才结束开发循环，不因此新增验收指标。普通文本完成声明不结束任务。kind 取 task_blocked 或 planning_conflict，其处理分别为未完成停止与第 7.1.4 节的定向规划交接；新增参数属于目标协议，当前代码尚未实现。

验证响应至少包含代码版本、检查范围、各项状态、真实命令/退出码、关键失败和日志位置。区分“通过”“失败”“未执行或被环境阻塞”，空结果不能算通过；并给出是否允许结束项目的结果。模型不能自行减少检查范围或设置该结果。

Agent 可直接提交 checkpoint 获得编译测试反馈，不要求先自行运行相同命令。首版正式结果只来自平台验证入口，Bash 自诊断输出不直接登记为正式通过。平台在相同源码、配置和检查范围内可复用自身已有结果；状态或环境相关测试无可靠复用条件时重跑，不先建设通用验证缓存。

工具结果保留命令、exit code、耗时与有界输出，完整日志另存。长命令需能超时终止并清理相关进程，不能让后台写入与下一次编辑或冻结验证重叠。

### 7.4 上下文与会话

保留简洁需求、当前目标、相关代码、重要实现决策与最近失败。不在每次任务中重复整个架构、批次、契约与文件职责。

按 token 使用量和模型窗口决定压缩，留出输出与工具返回空间。60%/80% 可作实验起点，不作为跨模型统一硬标准。完整 assistant/tool 配对必须保留，压缩失败不得用空摘要替换有效历史。

按第 7.1 节使用统一开发角色连续实现与测试，避免每种工作都重新开启失去上下文的会话。复杂变更才实验开发环节的 Planner/Editor 分离；需要拆任务时，将相关决策和已验证行为传给后续任务。

### 7.5 能力里程碑和轻量 checkpoint

按用户可观察的完整能力划分，例如投票项目：

```text
可构建骨架 -> 创建并查询投票 -> 投票与防重复 -> 结果展示和必要页面 -> 最终回归
```

每个能力可同时涉及数据、服务、接口、页面与局部测试。无需固定经过 Domain/Persistence、API、Frontend 三个技术层阶段；纯 REST 项目也无需前端里程碑。

首版任务记录包含 id、目标、状态、相关验证和工作版本即可。完成状态需要对应验证过的代码版本；后续任务修改公共代码时，重跑相关回归。允许合并或细分内部任务，但不能借此删除 required 功能。

保存最近接受的源码 checkpoint 和当前候选，足以支持回滚。跨 run 恢复、复用和全部事件重放留待实际需求出现；原始 JSONL 继续保留。

### 7.6 验证与修复

第一版沿用全项目验证思路：开发过程中在一组连贯修改完成后，编译整个当前项目并运行全量已有测试；编译失败时先返回编译错误，修复后再继续测试。这里的“全量”指当前项目的源码和已有测试，不是要求每次提交都已经实现所有业务，也不是每次加入所有可用的检查工具。初始 Bootstrap 仍按脚手架编译处理；尚无业务测试时如实记录，不能把测试缺失当成业务通过。

progress 用于获得反馈和发现跨文件回归，final 用于请求整体交付并执行既定最终验收，包括已有的项目契约等检查。未来功能尚未实现时，progress 不因为完整契约中存在该功能就强制要求立即交付；当前实际编译或测试失败仍返回开发者处理。全项目验证通过与项目需求全部完成保持区分。

Agent 可以通过 Bash 运行单个测试或局部命令快速定位问题，这属于自诊断，不改变正式全量验证策略。验证放在连贯修改之后，不要求每写一个文件就跑一遍，也不要求先自行全量测试再提交 checkpoint 重跑。只有实际耗时已明显拖累开发时，再评估针对性测试选择。

基准验收维护在平台控制的位置；Agent 可编写开发测试，但不能用改写基准测试或修改测试执行配置制造通过。公开全部要求和接口约定，保留具体隐藏数据与测试实现。

首版反馈沿用真实命令、退出码、关键日志，加上相关文件和最近改动。后续再为高频编译/测试错误提取稳定诊断；行号应主要作定位信息，不能因移动几行就判成全新根因。

已通过的明确行为被破坏属于回归；新暴露错误或同数量不同错误需结合内容判断。在全局预算内允许有限中间尝试，停止时保留当前现场和最后可验证候选。

### 7.7 模型调用和预算

规划使用正确角色消息与输出结构，工具循环维持真实 assistant/tool 记录。对限流和临时连接错误做有限重试；模型请求重试与工具副作用重试分开，不盲目重复已执行写操作。

优先记录总费用、输入/输出 token、轮次、工具耗时和验证次数，并设置合理全局额度。按任务规模分配开发与收尾预算；引入多个里程碑后不能给每个里程碑无限复制额度。

历史四类会话使用的原有轮次上限可作为旧基线，但不作为目标角色设计的不变量。费用上限不等于每次都消耗相同 token；模型实验分别比较质量与成本，避免把“相同费用”和“相同 token”混为一个约束。

### 7.8 Windows 持久化和磁盘真相

```text
Windows: ai_generated_projects/<project_run_id>
                     ⇅ 当前项目读写绑定挂载
Container: /workspace
```

平台先在 Windows 创建项目，再将该目录挂载给候选容器。Bash 在 /workspace 修改的文件立即反映到 Windows，不需要任务结束后 copy-back；删除容器不会删除宿主代码，也不会撤销已发生的删除或修改。

候选代码以磁盘为准，WorkflowData.codes 作为兼容现有服务的派生缓存，在需要时重新加载。Bash 与 patch 写入串行；验证前停止在途写入并确定源码版本。源码快照排除 target、日志与缓存，避免构建噪声扩大扫描和存储成本。

宿主执行 patch 时也必须检查实际目标位于项目根目录内；容器隔离不能代替宿主文件操作的路径约束。正式验收使用不会被 Agent 同时修改的候选版本，回滚由源码 checkpoint 实现。

### 7.9 依赖和缓存：先让受控构建可靠

固定当前 Java/Spring Boot/Maven Profile、基础依赖和可信仓库来源，优先使用一份 E 盘共享 Maven 缓存，例如 `.studio-cache/maven/repository`。不为每个项目复制完整 .m2，也不默认挂载用户个人配置和凭据。

依赖由 Maven 解析，平台负责触发预取或在缺依赖时补取，无需自行实现 Maven 依赖图解析器。预取应覆盖实际会执行的构建与测试命令；最小编译成功不能证明测试插件及运行依赖已齐全。

第一轮可先只支持常用依赖组合与配置化版本策略。模型新增依赖经允许来源解析和真实构建验证；不要求所有业务能力都先进入庞大 DependencyCatalog。不存在的坐标或不兼容版本反馈给代码/规划修正，网络故障和缓存故障作为环境问题处理。

Agent 对缓存的写入边界需要实际测试。可先尝试平台预取、候选离线只读使用；如果当前 Maven 工作流需要元数据写入，再验证只读基础缓存加少量可丢弃写入层，或经受控仓库获取的替代方案。不能未经测试就承诺完全只读一定可行，也不能因首次缺依赖就让模型反复改源码。

缓存维护首轮只需避免整仓复制、观察占用和在必要时清理无用版本。完整单写者服务、cache manifest、校验重建和自动淘汰不作为阶段一前置条件。镜像、Maven 缓存、项目 target 和源码应区分占用；历史个人 .m2 约 2.76 GiB 的测量仅作背景，不决定新的硬配额。

### 7.10 Hardened SandboxRunner

开放通用 Bash 时同时交付必要隔离：只挂载当前项目、无 Docker socket 和宿主凭据、使用固定可信镜像、非 root、合理资源与 PID 限制、取消和超时清理。按镜像验证只读根文件系统、tmpfs、cap-drop 和 no-new-privileges 的组合。

候选容器默认断网，需要依赖时由平台受控预取或受限来源访问解决。完整 Bash 的边界依赖容器、挂载与网络，而非命令前缀白名单。容器隔离是降低宿主风险的工程边界，不将其表述为绝对安全保证。

持久容器减少反复启动开销，每次命令仍明确 cwd 和环境，不依赖上一次 shell 的 cd/export。镜像预装实际使用的 Bash 和搜索工具；若实际使用 sh，接口和提示也应如实说明。

这些要求随阶段二的 Shell 一起实现，不拖到最后阶段才补。更复杂的多租户隔离和依赖治理根据部署范围另行评估。

### 7.11 其他实现歧义的默认处理

以下是第一版实现选择，用来收敛前文的可选路径；不是新增阶段或门禁。

| 问题 | 第一版安排 |
|---|---|
| 多大项目需要拆任务？ | 默认连续开发，规划可提出能力顺序；有多个可独立验证能力且跨度明显时才启用任务推进，不以固定文件数强制拆分 |
| 没有 milestoneId 如何验证？ | 默认编译整个当前项目并运行全量已有测试，不依赖任务标识选择子集；progress 返回反馈继续开发，final 请求既定整体收尾验收 |
| 声明要完成时额度恰好耗尽？ | 平台仍对已保存候选执行可用的最终验证并如实报告，不再增加模型修复调用；Agent stop reason 与产物验收结果分开记录 |
| 任意需求没有完整独立测试怎么办？ | 报告已验证行为和覆盖缺口；构建通过或模型自检不能据此升级为“全部需求已验证” |
| 新增 Maven 依赖如何触发下载？ | 开发者修改允许范围内的 POM，checkpoint 时平台预检和补取允许来源依赖；非法坐标反馈修复，不额外增加依赖管理 Agent |
| 模板何时覆盖已有文件？ | 只在初始脚手架阶段渲染；业务开始后构建修改作为明确补丁处理，修复和规划调整都不整模板重写 |
| patch 部分成功怎么处理？ | 先校验补丁结构和匹配，再写入；实际发生部分写入时返回具体已应用与失败项，并以磁盘重建状态，不重发全部已成功编辑 |
| 如何冻结待验代码？ | 首版顺序执行工具，等待相关命令及后台写入结束后保存源码快照，在独立验证副本运行检查；结果关联源码与配置版本 |
| 验证副本会不会复制 Maven 仓库？ | 仅复制必要源码和项目配置，复用依赖缓存；target、日志、平台验收资产不从候选目录当作可信结果复制 |
| 回滚和提交如何持久化？ | 首版由平台保存最近接受的源码快照，回滚只恢复当前项目受管源码和配置；不要求模型执行 Git commit，也不建设跨 run 重放 |
| 预算结束后的当前候选和较好候选如何交付？ | 保存最后现场；若恢复到较好版本作为交付，应明确该版本及其验证范围，不能把另一个候选的绿色结果附到它上面 |

持续后台服务如页面预览由平台跟踪并在验证、快照或结束时停止，不允许遗留进程继续写工作区。源码快照为版本一致性服务，不因此引入每条工具调用都复制整项目的策略。

## 九、分阶段实施方案

采用一个前置基线加四个阶段。阶段是交付主题，不要求每个支撑组件独立建设；基础实现—验证—修复从最早可运行路径开始存在，后续阶段提升其能力。

| 实施单元 | 核心目标 | 第一份可检查交付 |
|---|---|---|
| 前置基线 | 判定需求行为和真实成本 | 两个案例的外部行为测试与结果记录 |
| 阶段一 | 准确信息与稳定起点 | 输出协议修复 + 确定性可构建脚手架 |
| 阶段二 | 跑顺单 Agent 执行反馈 | patch + 容器 Shell + 精简上下文 + 统一验证反馈 |
| 阶段三 | 大任务可逐步交付 | 按需业务里程碑 + 轻量 checkpoint |
| 阶段四 | 提高修复与回归效果 | 高频错误诊断 + 更好的候选保留与行为回归 |

### 9.1 前置基线：建立需求一致的判卷方式

先选短链接和投票两个案例。短链接验证创建、访问、查询与无效链接处理；投票验证创建、投票、结果与明确约定下的防重复。先明确必要的接口和身份约定，避免不同实现被测试的隐含假设误判。

保存需求版本、源码提交、模型配置、费用/轮次、停止原因、项目路径、真实构建与行为结果。平台异常、环境失败和生成代码失败分别记录；同时保留全工作流成功率，不能把所有平台失败排除后只报告较好数字。

- 补充阿里百炼平台的缓存命中率观测，使任务报告能够统计百炼返回的缓存命中 token；

此阶段不承诺生成质量上升，交付标准是两个案例有可执行且需求一致的判卷方式，同一产物重复评价结果稳定，失败有产物或明确原因。风险是扩大需求或绑定内部类名；先审查验收来源，再运行模型。

### 9.2 阶段一：准确规划输出与确定性脚手架

修改 AbstractJsonAgent、规划 Agent 和模型请求边界，正确传递 role，提供准确嵌套 schema，移除 GET / 默认值。对已知关键字段做简洁检查；无歧义值可以确定性推导，真正缺失再定向修复。常规一次修复可作初始设置，不把固定重试次数升级为不可调整的架构约束。

本阶段完成 PlanningAgent 的需求/设计两步，原产品经理、架构和契约入口退出新主链。需求步骤测试明确功能不被删减，设计步骤测试字段缺失反馈和接口与需求的对应；不再默认维护架构和契约两套互相修订的模型输出。为区分效果，可先验证原角色的 schema 修复，再比较职责合并，不要求将两种收益混作一个结果。

从 ProjectProfileService 提取本地脚手架生成，创建 POM、入口、配置、目录与启动测试。依赖先通过固定 Profile 和共享缓存解决，执行真实最小编译；不以完整 DependencyCatalog、PlanIR 或符号图为前置。

这一阶段让模型更容易获得可用任务，移除固定样板工作。关键指标是关键字段缺失与误默认、脚手架构建结果、模型用于基础工程的轮次和首次业务编辑时间。用同需求、同模型对照观察，不能只统计规划拒绝率下降。

第一份交付应让两个案例进入业务编码前已经有可构建骨架，并能明确报告规划无法恢复的字段。若阻断大量本可正常实现的需求，应收窄检查；不要用更多规则弥补不清楚的输出协议。

### 9.3 阶段二：跑顺单 Agent 的实现—验证—修复

改造 WorkspaceToolRegistry、Runtime、Compactor 和 DockerSandboxService。先实现多文件 patch、新建文件直接表达、局部失败反馈，再接持久容器 Shell 和必要隔离。提供精简目标、相关文件与按 token 压缩的历史。

引入 submit_checkpoint 统一执行全项目编译和全量已有测试并返回真实反馈，让同一开发 Agent 可编写当前业务测试并修正实现。移除“一定先开发全部生产代码，再另起测试会话”的强制分隔，防止外层服务重复运行同一轮已完成的验证。第一版不实现自动局部测试选择，Bash 局部测试仅用于自诊断；外部基准验收仍由平台维护。

本阶段同步更新角色 prompt、WorkspaceAgentMode 的调用点和工具写权限：DevelopmentAgent 能改生产代码、前端和开发测试，平台验收资产仍隔离。实现 progress/final 与 planning_conflict 的不同处理；旧前端/测试/修复 Node 不能在新循环之后再各执行一轮。角色合并以真实调用链和权限变化为准，不以类重命名为完成标准。

针对性测试至少覆盖：测试暴露生产缺陷后同会话可修生产代码；progress 通过不会提前结束项目；final 失败返回开发、通过才完成；规划冲突处理保留工作区并续接；旧会话不会被重复调用。随后用真实生成产物验证质量收益，平台测试通过不替代第 10.5 节的效果检查。

收益应来自更少协议错误和重复读取、更早获得验证反馈，以及更多预算用于业务实现。记录 patch 首次成功率、首次正式验证轮次、重复构建耗时、行为通过率与单位成功任务成本，不要求工具调用总数一定下降。

第一份交付是两个案例能够从骨架开始，在一个连续开发循环内多次执行真实修改—验证—修复，并获得可信最终结果。若相同预算下仍不完成，查看剩余工作和末段进展，分别测试预算、模型与任务大小；不直接推定必须添加调度层。

### 9.4 阶段三：按需要引入业务里程碑

对阶段二中仍因任务跨度、上下文或中断而失败的案例，合并 SlicePlanningService 与 BatchPlanningService 的有效职责，形成业务任务列表。按“创建并查询”“投票与防重复”等用户能力推进，允许一次跨多层文件修改。

小项目可继续单任务完成。任务列表不必在编码前冻结全部内部文件；允许合理调整，保留 required 用户行为。每个完成任务记录对应验证和源码版本，保存最近接受的 checkpoint；后续公共代码变更触发相关回归。

效果看首次完整能力通过时间、全项目行为结果、上下文消耗和中断后的重复工作量。不能因为任务数增加、每个任务获得新的预算，就宣称调度提高了效率；比较时继续使用全局预算。

交付标准是拆分确实改善受影响案例，且不会让简单案例增加无用规划与验证。恢复先支持最近 checkpoint；完整 Manifest、跨 run 复用和事件重放仍按真实需要决定。

### 9.5 阶段四：补强诊断、候选保留与行为回归

根据已有轨迹中高频失败，逐步结构化编译、测试和契约反馈；FailurePack 先包含根因线索、相关代码、命令与最近 diff，不要求覆盖全部语言和验证器。

改造单轮 NO_PROGRESS 即停止的策略。保存最后可验证的较好候选，在预算内允许合理探索；候选比较优先考虑已通过 required 行为是否保持，不机械要求错误数量下降。对环境问题进行受控重试或明确停止，避免让编码模型修网络。

扩大有价值的外部行为与回归覆盖。真实 UI 需求增加浏览器 smoke，WebSocket 需求增加协议行为验证；这些检查随需求加入，不作为所有项目的统一清单。

指标包括修复后行为通过率、重复根因、已通过能力退化、修复成本和错误归因。若更复杂诊断不能改善下一轮修复，保留关键日志即可。RepoMap、双模型分工仅在已出现相应瓶颈时做小实验，不能变成此阶段必须交付的附加平台。

### 9.6 阶段之间的依赖与持续实验

必要依赖是：可信验收支撑比较、脚手架提供执行起点、容器隔离伴随 Bash、实际版本关联支撑 checkpoint。不存在“阶段二必须先降低 turn-limit，才允许改工具”这样的因果前提。

模型和预算对照可从基线开始穿插，主要用于判断剩余瓶颈；复杂路由和大规模模型矩阵后置。对互相制约的改造，可以先测组合是否形成闭环，再分别移除组件观察贡献，不要求每项孤立时都必须见效。

## 十、验证方法与保留标准

### 10.1 从小样本诊断到正式比较

先验证固定产物的验收，再用两个案例做少量 smoke 检查链路。发现明显失败后回到源码和轨迹定位；不必每次改动都运行六案例、多轮、全模型矩阵。

初步有效后扩展到现有六案例并重复运行。每变体每案例 5 次可作为初始采样规模，不代表自动获得统计显著性。逐案例报告成功次数、成本和波动，不以一次成功替代稳定改善。

当前同实例先串行执行不同 run，避免进程级指标与目录、资源相互影响。单任务中的独立只读动作可批量执行，写入保持串行。

### 10.2 对照设计

| 比较 | 保持不变 | 主要观察 |
|---|---|---|
| 原输出协议与准确 schema/role | 需求、模型、后续执行 | 关键字段缺失、错误契约与行为结果 |
| 空目录与平台脚手架 | 业务目标、模型、总预算 | 基础缺陷、业务编辑时间、完成成本 |
| 原工具与新 patch/Shell/上下文 | 模型、任务、脚手架与验收 | 协议失败、首次验证、行为结果 |
| 连续单任务与能力拆分 | 工具、模型、总预算与验收 | 大任务完成率、重复工作和简单任务开销 |
| 原修复与改进反馈 | 相同失败候选、模型与预算 | 修复转化、回归和成本 |
| 不同模型或预算 | 需求、工具、验收和环境 | 实际质量—费用—时间变化 |

无需一次运行全部组合。先沿实施路线比较，再针对效果来源不明的部分做拆分实验。工具和任务拆分的交互值得单独观察，不能把阶段累计收益全部归给最后一个组件。

### 10.3 结果口径

主量化指标为需求一致的行为通过率和完整工作流成功率，同时结合生成源码质量检查评价整体效果；辅助报告耗时、费用、验证到达率、协议失败和重复工作。生成目录、diff、平台 success、编译绿色均不能单独证明业务完成。

规划阻断应计入整体工作流结果；没有进入编码不等于优化成功。缩小测试分母、增加每里程碑额度或改变模型，都需明确说明，不能与原口径直接比较。

保留能够改善对应瓶颈且成本合理的改造；仅增加状态、校验或日志的机制按可维护性和实际恢复需要判断，不包装为直接生成收益。硬性失败判定依据明确 required 要求，未知项和未覆盖项如实报告。

### 10.4 生成源码本身的质量评价

行为测试通过不能涵盖全部代码质量。比较重构前后的生成产物时，还应检查明显的重复业务逻辑、不合理职责划分、依赖硬编码或偶然条件才能工作的脆弱实现，以及必要异常处理缺失。评价应结合具体需求与项目规模，说明相关文件、代码片段及其对正确性或后续修改的实际影响，不能仅凭类数量、代码行数或命名风格给出优劣结论。

沿用同一组检查关注点比较代表性产物，可通过人工源码审查并辅以适用的静态工具完成，不另建一套强制评分平台。发现会破坏明确需求的缺陷时，应尽可能补充对应行为用例；一般可维护性问题作为质量证据和改进反馈，不全部转为运行时硬门禁，也不强制套用某种分层或设计模式。

最终效果结论同时说明行为结果与源码质量变化。测试通过率提高但实现明显变脆弱，或代码更整齐却缺少必要功能，都不能笼统宣称生成代码全面改善。

### 10.5 区分实现完成与效果验证完成

某项改造接入实际主链，并通过相应平台测试，只能说明该能力已经实现、基本可用；它不能替代对真实生成项目的检查。尚未完成真实生成对照时，交付应明确标记“已实现，效果待验证”，不把工具可调用、流程可运行或平台测试绿色写成生成质量提升。

效果验证需要在明确的需求、模型、预算和环境条件下检查真实生成产物，对照行为结果及源码质量，并记录适用案例和局限。已有对照支持改善时，说明改善体现在哪里；结果不足或未见改善时，如实标记证据不足或效果未达预期，再决定调整、简化或撤回。每个阶段的交付分别说明实现状态与效果状态，不增加新的实施阶段或验收框架。

## 十一、哪些可移植，哪些暂缓

可优先按 Java 实现参考的机制包括：简洁 Agent/Model/Environment 边界、多文件 patch 表达、编辑失败反馈、有界工具输出、完整轮次压缩、实际验证结果和持续轨迹记录。

需要结合本项目设计的机制包括：绿地脚手架、Windows 工作区与容器协作、任意 Bash 写入的状态发现、业务能力拆分、公开接口与外部验收对齐。它们不能因参考项目有相近名字就视为已验证方案。

暂缓完整规划编译器、提前封存全部实现步骤、跨 run 复用、事件重放、全语言诊断路由、完整符号图和自动多模型调度。需要时再引入，不设为第一轮成功的前置条件。

本地根许可证文件显示：OpenCodeReview、Codex CLI、Aider 为 Apache-2.0，mini-SWE-agent 为 MIT。具体复制代码前记录仓库、文件与提交，保留适用的版权和许可证信息，并核对相应 NOTICE 和文件声明；“机制可借鉴”不等于某个成熟模块可以无改动粘贴进 Java 工程。
