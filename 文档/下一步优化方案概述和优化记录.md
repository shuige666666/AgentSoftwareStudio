### 7.3（缓存命中率）

我现在就在进行 token 的缓存命中率优化前先补充了一层指标，这样下次进行缓存命中率之前可以先进行测试和记录指标，然后优化后再测试记录看看有没有做到真的提升。

已补上指标采集，核心改动如下：

在 [LlmUsageMetricsService.java](/mnt/c/My Space/Other Projects/agent 软件开发小组/agent-software-studio/src/main/java/com/core/multiAgentSoftwareStudio/Agent/LlmUsageMetricsService.java) 新增了本次任务级别的 LLM 用量统计，会累计：

- `输入Token(命中缓存)`
- `输入Token(未命中缓存)`
- `输出Token`
- `总Token`
- `远端输入缓存命中率`
- `LLM调用次数 / 成功 / 失败 / 总耗时`

在 [ObservedDeepSeekChatModel.java](/mnt/c/My Space/Other Projects/agent 软件开发小组/agent-software-studio/src/main/java/com/core/multiAgentSoftwareStudio/Agent/ObservedDeepSeekChatModel.java) 新增了 DeepSeek OpenAI-compatible 调用包装器。它不做 prompt 重排、不做缓存优化，只是调用 DeepSeek API 后解析 `usage.prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`、`total_tokens`。这些字段是 DeepSeek 官方文档里给出的真实 usage 字段，精度比本地估算可靠：[DeepSeek Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion)、[Context Caching](https://api-docs.deepseek.com/guides/kv_cache)。

控制台单次输出会是中文，例如：

```
[LLM用量] 第3次 阶段=DeveloperAgent 模型=deepseek-v4-flash 耗时=8421ms 输入(命中缓存)=12480 输入(未命中缓存)=3912 输出=1840 总计=18232 远端输入缓存命中率=76.13%
```

任务结束时会输出汇总，并且通过原有 SSE 日志推到前端：

```
[LLM用量汇总]
LLM调用次数=18，成功=18，失败=0，总耗时=143280ms
输入Token(命中缓存)=84210
输入Token(未命中缓存)=61740
输出Token=28630
总Token=174580
远端输入缓存命中率=57.70%
```

前端 [stream_chat.html](/mnt/c/My Space/Other Projects/agent 软件开发小组/agent-software-studio/src/main/resources/static/stream_chat.html) 也加了 `usage` 分类样式，所以这些汇总会在日志区域里单独标识出来。



### 7.10（生成质量优化）

优化前要做的第一步首先是要有一个衡量标准，衡量生成的程序质量如何。

在这之前有添加一个缓存命中率的显示。

**生成质量基准测试（7.10）**

新增了两个接口：`/benchmarks/cases` 用来查看内置基准用例，不调用 LLM；`/benchmarks/run` 用来显式执行基准测试，会真正调用生成工作流、消耗模型额度，并保存运行报告。

新增了 `Service/Benchmark` 模块，包括基准用例、运行请求/报告、单用例结果、质量门禁和质量评估器。评估逻辑把“平台流程成功”和“独立质量通过”分开判断，会检查是否有占位实现、是否生成测试代码、测试是否真的执行且通过、是否包含 Spring 上下文测试等。

还调整了生成工作流返回值：新增 `WorkflowExecutionResult`，让工作流除了返回源码外，也能带回项目路径、测试结果、平台成功状态和 LLM 用量统计，供基准测试报告使用。



### 8.8（重构结构和补基准测试的指标）

1. 重构了一下项目结构，让 record 放的位置稍微标准化一点
2. 把模型从 deepseek 换成了千问，虽然好像也是差不多慢，但是效果好像稍微好一点点。
   - 然后由于之前缓存命中率的设置是对 deepseek 专属的，所以说切换模式的话这个指标得有所改动。然后我最后的选择是保存了旧的指标，然后把这个指标设置成了策略模式。
   - 当 application.yml 中的 studio.ai.provider 为“alibaba-bailia”的时候才开启记录缓存命中率，为其它平台的时候就显示为 N/A。
   - 后续假如需要优化缓存命中率的话再补阿里百炼平台的这个指标的记录。
3. 增加基准测试指标
   - 一开始主要是怀疑 AiConfig 中的那个 `MAX_OUTPUT_TOKENS` 和 `MODEL_TIMEOUT` 到底有没有用，会不会影响到最后的代码输出？
   - 于是增加了几个错误类型，在基准测试结果里补了几个指标。主要是用于记录输出有没有被截断、输出有没有超时。
   - 补完之后测了一下好像这几个错误都没有出现，于是这两个配置就先保留着不动了。
