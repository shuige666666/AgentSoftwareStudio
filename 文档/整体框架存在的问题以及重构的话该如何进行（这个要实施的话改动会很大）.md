### 当前问题

**一条链路从一句自然语言 prompt 直接生成一个“质量稳定、结构正确、可运行、可维护”的完整项目，确实很难**。不是完全做不到，而是不能把它设计成“瀑布式一次生成”。Codex、Claude Code 这类工具更接近“带工具的工程师”：读代码、改一小块、运行命令、看失败、再修、再验收，并且过程中允许人类补充约束和审查结果。

你现在这个系统更像“多 Agent 流水线”：PM 写 PRD、架构师出结构、开发者生成文件、测试者生成测试、Debugger 修复。这个方向有价值，但如果它从头到尾只靠一条自动链路推进，最大问题是：**前面某一步的含糊或错误会被后面所有步骤继承，最后修复器只能在一个已经偏掉的世界里打补丁**。

**Codex/Claude Code 通常不是这样工作的**

以 Codex 为例，官方手册里强调的不是“给一句话自动生成完整项目”，而是把 Codex 当作一个可配置、可验证、可审查的队友使用：给目标、上下文、约束和“完成标准”；复杂任务先规划；把长期规则写进 `AGENTS.md`；让它运行测试、检查 lint、确认行为、 review diff。官方 prompting 文档也明确说，Codex 在一个循环中调用模型并执行文件读取、文件编辑、工具调用，直到任务完成或被取消；复杂任务更适合拆成更小的 focused steps。参考：[Codex best practices](https://developers.openai.com/codex/learn/best-practices) 和 [Codex prompting](https://developers.openai.com/codex/prompting)。

Claude Code 这类编码代理公开使用体验上也类似：它不是只输出一个 zip，而是在本地仓库里持续读文件、编辑文件、跑测试、看报错、再修改。真正提升质量的关键不是“模型一次想对所有事”，而是让模型能不断拿到真实反馈。

**为什么一条自动链路容易失真**

你现在遇到的问题很典型。用户说“包含前后端”，系统可能理解成 Spring Boot 静态资源；用户说“Node14 前端”，生成物却没有 `package.json`；测试代理可能发明一个 `WS_URL` 字符串格式要求，而开发代理用了模板字符串；前端发 `RESTART`，后端只解析方向枚举。它们都不是语法层面的低级错误，而是**契约没有被稳定地共享**。

一条链路最大的问题是每个 Agent 都在“局部最优”。PM 觉得需求够了，架构师觉得目录够了，开发者觉得文件能编译，测试者觉得断言能表达需求，Debugger 只盯着报错修。但一个好项目需要全局一致性：运行环境、目录形态、接口协议、测试边界、用户交互、部署方式都要对齐。这个全局一致性很难靠一次性自然语言传递。

**更现实的生成方式**

更靠谱的方式是把“生成项目”改成“分阶段收敛项目”。

第一阶段不要写代码，而是生成一份可审查的项目规格：项目形态、技术版本、目录结构、接口协议、运行命令、验收标准。比如用户说 Java8 + Node14，就必须先明确是 `backend/` + `frontend/` 两个子项目，还是 Spring Boot 静态页面。如果用户没说清楚，系统可以默认一种，但要把默认写进规格。

第二阶段只生成骨架和最小可运行闭环。例如后端启动、前端能打开、一个 API 或 WebSocket 能通。这个阶段的验收是启动和冒烟测试，不追求功能完整。

第三阶段按功能切片生成。计算器先做加减乘除接口和页面，再做错误处理；贪吃蛇先做后端状态 tick 和 WebSocket 状态推送，再做方向控制，再做重启，再做游戏结束 UI。每个切片都有自己的测试和验收。

第四阶段做质量审查。这里不是让 Debugger 无脑修 surefire，而是先判断失败属于实现错、测试错、契约缺口，还是环境不一致。比如 `WS_URL` 那个问题，本质上是测试过窄；`RESTART` 无效才是实现错；Java8 跑不了 Spring Boot 3 是架构约束错。

**你这个系统可以怎么向 Codex/Claude Code 靠近**

不要取消多 Agent，但要把它从“流水线”改成“可回退的工程闭环”。Contract 应该成为中心，而不是附属文档。Developer 和 TestWriter 都只能根据 Contract 工作；如果测试发现 Contract 没说清楚，应该回到 Contract 阶段补协议，而不是让 Debugger 猜。

同时要增加 deterministic quality gates，也就是不靠 LLM 判断的硬门禁：Java8 不能用 Spring Boot 3；Node 前端必须有 `package.json`；`No tests to run` 不能成功；Spring 项目必须有 context 启动测试；构造器注入的类必须是 Bean；WebSocket/HTTP 路径必须和契约一致。这些规则比多调用几次模型更稳定。

另外，复杂项目最好引入模板。Codex/Claude Code 通常是在已有仓库里工作，已有仓库天然提供了结构、依赖、测试命令、风格约束。你的系统是从零生成，所以更应该给它“标准项目模板”：Java8 Spring Boot 2 REST、Java8 WebSocket、Node14 前端、前后端分离等。LLM 填业务逻辑，模板保证工程骨架。

**最终判断**

所以答案是：一条链路走到底不是完全不可行，但如果它是“自然语言 -> 多 Agent 各自生成 -> 最后修复”，那生成好项目会很难，而且越复杂越不稳定。更接近 Codex/Claude Code 的路线应该是：

先规格化，再生成最小闭环；按切片迭代；每步运行真实检查；失败先分类；必要时回退到契约或架构；最后由测试和 review 共同放行。

也就是说，你要优化的不是“让一个流水线更聪明”，而是让它变成一个**有规格、有反馈、有回退、有门禁的工程循环**。



### 重构设计（后续可以再完善，这是初版大纲）

**目标形态**

重构后建议变成这个形态：

```
需求规格化
  -> 架构/契约确认
  -> 创建真实工作区
  -> 按垂直切片实现
       -> 写/改少量文件
       -> 运行对应验收
       -> 失败分类
       -> 修实现 / 修测试 / 修契约 / 修架构
       -> 再验收
  -> 全量质量门禁
  -> 最终 review
```

你要做的不是把 DeveloperAgent 和 DebuggerAgent 物理合并，而是把它们放进同一个闭环里：**Developer 负责实现当前切片，Verifier 给真实反馈，Triage 判断错在哪一层，Developer/Test/Contract/Architecture 按分类回修，直到该切片通过再进入下一片**。这就是从“生成流水线”变成“工程代理循环”的关键。
