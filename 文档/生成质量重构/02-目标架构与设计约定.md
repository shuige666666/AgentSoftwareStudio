## 2.3 正式范围

第一轮集中改善当前主要覆盖的 Java 17、Spring Boot、Maven 项目，优先使用已有 Profile 和模板。Web 页面、REST 与 WebSocket 的验收应按需求选择；现有贪吃蛇案例涉及 WebSocket，不能用 REST 检查替代。

纯 Java Maven、原生 Java 可以继续保留现有能力，质量结果按类型分别说明。第一轮不要求为所有类型同步建设新执行路径，也不因为暂未覆盖某类型就大规模增加产品状态体系。

第一轮沿用单次需求输入，不建设需求访谈和等待恢复接口。模型可以对未指定的普通设计细节形成显式假设；不能擅自增加 required 功能，也不能通过忽略核心要求宣称完整成功。

<a id="section-6"></a>

## 六、改造原则与边界

本次重构的首要目标是提升最终生成项目的代码质量：功能符合需求、实现完整、逻辑正确、跨文件和前后端一致、能够构建运行，并具有与项目规模相称的可维护性。开发中的取舍先看生成代码是否更好，再看增加的平台复杂度和成本是否值得；不能为了减少工具调用、缩短运行时间或简化平台，牺牲必要功能、验证和修复。

脚手架、规划、工具、上下文和修复改造都是服务于这一目标的手段，其质量收益仍需真实产物验证。调用减少、运行加快、日志完善或平台更严谨，只能作为辅助证据；如果生成代码质量没有改善，就不能据此宣称重构目标达成。仅增加管理复杂度、又未帮助生成质量的设计应降低优先级或撤回；必要的执行隔离、持久化和验证可信性仍作为基础能力保留。

平台负责工作区、预算、工具执行、可信验证和结果记录；Agent 负责提出并实施代码变更。最终成功来自实际验证，不能由模型自述决定。

稳定的是用户要求、公开接口约定与基准判卷口径；内部文件布局、方法和任务拆分允许调整。发现计划错误时应反馈、修正和重新验证受影响行为，不能靠冻结错误计划维持表面一致。

首轮只对会破坏执行或结果可信性的实际问题设置阻断：关键目标无法确定、构建失败、明确 required 行为未通过。风格、可选功能、未知覆盖和普通建议分别报告。检查数量本身不是质量指标。

诊断、日志、缓存、快照和内部状态是支撑能力，不应各自变成额外关卡。基础设施异常仍可能终止执行，但不能被误记成代码语义错误。

## 七、推荐目标架构

<a id="section-7-1"></a>

### 7.1 一条简单主链

```text
用户需求
  -> PlanningAgent：需求整理 -> 总体设计与公开接口约定
  -> 关键字段校验/明确缺失的定向修复
  -> 平台生成可构建骨架
  -> DevelopmentAgent：开发循环
       读取/搜索 -> 修改 -> 平台验证 -> 获得失败反馈 -> 继续修改
       小项目可在一个连续会话完成
       大项目按业务能力逐步推进
  -> 最终需求行为验收
  -> Windows 项目代码与结果报告
```

实现初期复用现有 WorkflowData 和结果模型，不必一次新增六个中间模型。必要的新结构可以先限于脚手架输入、当前任务说明和验证反馈。

<a id="section-7-1-1"></a>

#### 7.1.1 默认两个模型角色，平台承担执行管理

目标主链固定为统一规划角色 PlanningAgent 和统一开发角色 DevelopmentAgent。这里的角色是职责和上下文边界，不代表必须使用两个模型，也不代表只能调用两次模型。第一轮沿用已有模型配置，不因角色重构强制引入多供应商路由。

| 角色/组件 | 负责什么 | 输入与输出 | 权限和完成边界 |
|---|---|---|---|
| PlanningAgent | 整理需求、总体设计、公开接口、必要业务任务建议 | 原始需求与平台 Profile；输出需求摘要和设计约定 | 不写生成源码、不执行 Shell、不修改外部判卷要求；平台检查关键字段后交给开发 |
| DevelopmentAgent | 实现后端与前端、编写开发测试、联调、阅读失败并修复、检查源码质量 | 原始需求、有效规划、真实工作区与验证反馈；产出磁盘改动和验证请求 | 可修改当前项目的生产代码和开发测试；不能修改平台验收资产或自行设置成功 |
| 平台服务 | 脚手架、工具执行、依赖准备、验证、状态同步和结果保存 | 接收结构化规划和工具请求；返回真实结果 | 决定当前代码版本和验证状态，不通过增加“管理 Agent”执行确定性工作 |

规划角色合并的是职责归属，开发角色合并的是编码责任和工作上下文。测试设计、前端联调和修复仍要做，只是不再默认分配给相互失去上下文的独立会话。

PlanningAgent 负责前期形成目标，并在必要时协助修订，不作为开发过程中的常驻审批者。进入编码后，DevelopmentAgent 是持续推进工作的主体；两个角色不要求建立两个常驻进程，也不要求按固定轮次来回讨论。规划角色是否独立保留，最终仍依据其对生成质量的实际帮助判断。

<a id="section-7-1-2"></a>

#### 7.1.2 PlanningAgent 的两步输出

第一版默认由同一规划角色分两次模型调用完成规划。第一步形成需求摘要，第二步基于原始需求和该摘要形成总体设计与公开接口；不强迫一次回复生成全部结构。简单项目是否合并为一次调用，后续通过对照决定。

需求摘要包含项目目标、具有稳定标识的用户行为、关键业务规则、符合需求的行为表现、明确技术限制、合理假设和未解决问题。行为表现用于解释已有要求及必要的异常情况，不借此扩充必需功能。保留原始需求，避免只传 PRD 后逐层丢失用户要求。不得以“MVP”或“范围可控”为理由删除用户明确功能；可选建议与必需行为分开记录。

设计输出包含项目包名/入口、平台 Profile、关键领域职责、外部接口或页面交互，以及实现建议。HTTP 接口明确 method、path、输入字段、输出字段与必要错误语义；WebSocket 和页面项目使用对应协议/交互约定，不强制套成 REST。每个必需行为应说明由哪些可观察接口或交互实现，但不要求预测全部内部类、方法和文件。

总体设计还应按业务需要说明关键领域对象及关系、核心业务流程、必要的状态变化和数据保存方式；权限、并发或事务要求只在相关场景中展开。例如借用业务需要说明设备与借用记录的关系、归还允许的状态，而不能只定义两个接口的字段。关键规则在实现对应业务前明确，具体表结构、类和方法可在开发中完善，不强制新增独立数据库设计书或冻结全部内部实现。各类文档的职责与维护方式见[第 7.1.8 节](#section-7-1-8)。

首版可以复用 PrdDocument、ProjectStructure 和 ProjectContract 作为内部适配结构，新增字段只围绕上述实际需要。对模型暴露的 schema 必须完整且无歧义，不照搬冗长对象 toString()。设计步骤合并原架构和契约职责，避免两者反复重述、各自修改接口。

缺失字段反馈给产生它的步骤；可以确定性推导的值由平台补全并说明来源。基础依赖预取和脚手架渲染属于平台动作，不再调用规划模型确认普通文件操作。

<a id="section-7-1-3"></a>

#### 7.1.3 DevelopmentAgent 的工作协议

开发会话从已生成的骨架开始，默认持续负责完整项目。system 消息规定工具、质量要求与修改边界；任务消息提供原始需求、精简规划、当前能力和已知限制；工具消息提供真实操作与验证结果。不会将规划角色的全部讨论原样附加到开发历史。

精简规划仍应保留有效约定、关键设计理由和未解决问题，不能只给失去判断依据的结论摘要。更详细的规划内容和证据由平台保留，通过有权限的按需读取或定向调用输入提供；不必每轮重复注入全部规划与源码。

开发顺序是理解现有骨架、实现一个可验证单元、补相应开发测试、提交验证、根据反馈继续。前端任务包含端点、载荷、DOM/模板变量与错误状态检查；纯后端任务不额外创建前端。收尾时对照必需行为和[第 10.4 节](./03-实施路线与效果验证.md#section-10-4)检查明显源码缺陷，不新增强制的独立“质量 Agent”。

普通编译错误、测试失败和前后端不一致都由当前开发会话处理，不因为错误类别改变就重新分配角色。开发测试可修改，但应依据需求和失败证据纠正断言，不能删除有效测试或弱化正确断言以制造通过；平台外部验收始终不可写。

引入业务里程碑后优先在同一会话推进。上下文确实过大时可建立续接会话，传入当前代码版本、有效规划、已完成能力、关键决定与最新失败。续接仍是 DevelopmentAgent，不能把摘要当成已经验证的事实，必要时读取磁盘和验证记录确认。进程中断后的恢复在阶段三补齐最近 checkpoint 支持后再提供，首版先保证产物和日志可保留，不承诺自动恢复。

<a id="section-7-1-4"></a>

#### 7.1.4 规划调整、故障与控制权

类名、私有方法、文件拆合和其他不改变公开行为的调整，由 DevelopmentAgent 直接实施。普通代码缺陷不回到规划角色。发现实际需求与公开契约冲突时，开发者通过 report_blocker 的 planning_conflict 类别提交具体冲突、需求依据、相关代码或错误证据及建议，不直接更改判卷资产。

平台收到 planning_conflict 后暂停当前开发循环，携带相关需求、有效规划和冲突证据，定向调用 PlanningAgent 审查；这是本次 run 内可恢复的交接，不等于立即将整个 run 判失败。平台接收决定并更新必要的任务状态后，通过该次 report_blocker 对应的工具响应，将决定、理由和受影响内容返回原开发会话，保持 assistant/tool 调用配对；若有修改，应说明哪些旧约定被替代。保留现有源码和开发历史，按原会话继续，不重新生成骨架；只有上下文确实需要压缩或续接时，才按[第 7.1.3 节](#section-7-1-3)处理。拒绝无依据的变更时也应返回原因，让开发者继续按现有约定实现。

基准需求和公开接口约定在一次对照中保持不变，规划角色不能为让候选通过而修改它们；确需修正基准时，另建案例版本并重新对照。普通生成中，用户指定的接口不可自行改；规划阶段自行选择的接口确有缺陷时，可以形成新版本约定并重验受影响行为。独立验收的预期不能直接依据当前代码反向修改。

未知模型或运行时异常保留候选和原因，平台按已有重试策略处理；环境问题优先交平台处置，不让开发 Agent 通过修改业务代码修网络。普通 task_blocked 表示无法继续，由平台记录未完成原因。重复交接不能无限循环，沿用 run 级停止策略即可，不新增复杂角色协商框架。

<a id="section-7-1-5"></a>

#### 7.1.5 旧角色和执行模式的去向

| 当前入口/模式 | 目标安排 | 需要保留的有效职责 |
|---|---|---|
| ProductManagerAgent | 并入 PlanningAgent 需求步骤 | 原始要求、用户行为与合理假设整理 |
| ArchitectAgent + ContractAgent | 并入 PlanningAgent 设计步骤 | 工程类型、关键设计、公开接口与前后端约定 |
| SlicePlanningService + BatchPlanningService | 单一业务任务建议/推进逻辑；阶段三按需执行 | 用户能力的依赖顺序，不新增规划角色 |
| IMPLEMENT | DevelopmentAgent 默认开发循环 | 生产代码实现，同时允许开发测试 |
| FRONTEND_INTEGRATION / FrontendReviewNodeService | 有 UI 时融入开发任务与收尾检查 | 接口、页面、脚本和错误展示一致性 |
| TEST / TestGenerationNodeService | 融入开发循环，取消仅能写测试目录的模式隔离 | 有意义的测试与真实执行反馈 |
| REPAIR_IMPLEMENTATION / REPAIR_TEST / REPAIR_CONTRACT | 作为开发会话收到的失败类型，不再各自开启默认角色 | 真实错误定位与修复 |
| ToolDrivenRepairService 等外围控制 | 逐步收敛为平台验证、候选保留与停止控制 | 防止回归、保留证据，不另起完整修复链 |

当前独立 Java Agent 类与工具运行时 mode 不是同一概念；上表同时处理两者，避免只合并类名却继续按原模式重启会话。迁移期间可保留旧 DTO、事件名和适配入口，但新主链不能依次执行新旧两套逻辑。

<a id="section-7-1-6"></a>

#### 7.1.6 可选审查角色与双模型实验

首版不默认加入独立 Reviewer。若真实产物反复出现开发者自检遗漏，可增加只读审查步骤，读取需求、源码及验证结果，输出带文件依据和影响说明的 findings，再由 DevelopmentAgent 修正。审查意见不自动成为新需求，也不能凭一句“通过”代替平台验收。

Aider 式 Planner/Editor 分离特指开发过程中“提出具体变更”和“按格式编辑”的分工，与项目开始时的 PlanningAgent 不同。只有复杂修改确有收益时才尝试；首版开发者自己完成两项工作。可选角色的加入按生成质量结果决定，不以角色数量作为架构目标。

<a id="section-7-1-7"></a>

#### 7.1.7 任务状态、会话上下文与交接

采用“平台共享任务记录，Agent 通过明确输入和结果交接”的方式，不把 WorkflowData 当作所有 Agent 共同读写的聊天历史。三类信息分别管理：

| 信息 | 保存位置与职责 | Agent 如何使用 |
|---|---|---|
| 本次 run 的任务状态 | 复用 WorkflowData，记录原始需求、有效规划、工作目录、进度和最近验证结果；由平台更新 | 平台选择相关内容组成调用输入，不将整个对象每轮序列化进 Prompt |
| Agent 会话上下文 | 由运行时分别管理规划调用与开发会话的消息；开发保留连续的 assistant/tool 历史 | 通过当前任务消息、工具反馈和必要续接内容获得信息，不自动合并另一角色的全部历史 |
| 生成项目源码 | 以真实工作区文件为准，WorkflowData.codes 仅作派生缓存 | 通过工具读取、修改和验证，不能用会话里的旧代码描述替代磁盘现状 |

调用边界使用明确参数或少量输入输出 DTO：平台选取输入、调用角色、接收结果，再更新任务状态。不要求所有现有服务立刻停止使用 WorkflowData，但角色调用入口不应依赖随意读写整个可变对象来隐式交接；普通工具反馈直接回到开发会话，不必为每条消息增加一份共享状态字段。

更新 WorkflowData 不会自动让运行中的模型知道变化。凡影响后续实现的有效规划决定，都应按[第 7.1.4 节](#section-7-1-4)明确返回开发会话；后续构造上下文时使用有效版本，避免继续注入已被替代的约定。首版由普通程序完成上述顺序编排，不新增消息总线、团队任务认领、自由角色协商或专门的管理 Agent。

<a id="section-7-1-8"></a>

#### 7.1.8 设计文档与交付资料

面向开发者接手和继续修改业务原型，文档用于说明开发依据、关键设计、运行方法和实际完成情况，不以数量衡量流程是否规范。保留并细化现有需求、总体设计与契约信息，补齐 README／运行说明及验证与交付报告；已有对应资料时直接整理复用，不强制另建五份文件。

| 文档类别 | 职责与必要内容 | 形成时机与维护责任 |
|---|---|---|
| 需求／PRD | 目标用户与问题、必需功能、业务规则、技术限制、合理假设、未解决问题，以及符合需求的行为表现；保留原始需求依据 | PlanningAgent 在编码前形成；需求或关键约定调整按[第 7.1.4 节](#section-7-1-4)处理，不能为了迁就实现而删改要求 |
| 总体设计 | 模块职责、关键业务流程、领域对象及关系、必要状态变化、数据保存方式和关键设计理由；数据设计可直接放在本节 | PlanningAgent 形成关键设计；DevelopmentAgent 随实现补充不改变公开行为的内部细节，不预先穷举所有表、类和方法 |
| 接口／交互契约 | 对外接口的输入输出、必要错误语义，以及页面或其他协议的交互约定；说明跨模块或前后端如何配合 | PlanningAgent 与总体设计一起形成；公开约定变更走既有规划交接，不维护一份脱离有效规划的独立契约；简单项目可与总体设计合并 |
| README／运行说明 | 环境与外部依赖、必要配置及占位示例、启动和测试命令、必要的数据初始化方式、核心功能的体验步骤；不包含真实凭据 | DevelopmentAgent 随实现维护，交付前按实际工程配置和运行记录整理；未验证的步骤应说明，不将容器内执行成功等同于所有宿主环境均可运行 |
| 验证与交付报告 | 本次交付的源码版本、功能完成情况、实际执行的验证命令及结果、未执行或未覆盖内容、未完成项与已知限制，必要时引用详细日志 | 平台基于已有验证记录与结果模型汇总；DevelopmentAgent 可提供实现说明和待确认问题，但不能用模型总结替代真实通过／失败结果 |

内部 DTO 或会话消息不等于已交付文档。平台将有效需求、设计和契约导出为可阅读资料，优先复用结构化结果和简单模板，不为每份文档单独增加模型调用。README 放在生成项目根目录，其余资料随项目保存在清晰的文档目录，已有路径可复用；验证报告由平台生成并在交付时导出，不能让开发 Agent 改写平台保存的原始验证事实。

不要求所有文档在编码前一次完成。编码前提供关键目标和约定，开发中同步必要设计变化及运行说明，收尾时按实际保留或交付的源码版本整理资料与报告；失败或中断时也保留已有资料并说明未完成状态，不把前一次候选的验证结果套到当前代码上。正文只保存有效说明，历史原因可复用已有记录，不另建完整文档版本管理系统。

文档中的需求和公开约定是实现依据，源码与执行记录说明实际实现状态，两者不一致时按既有修复或规划调整流程处理，不能仅修改文档制造一致。文档供使用者阅读并供 Agent 按需取用，不因持久化了更多资料就每轮全部注入上下文。这些约定不新增文档专用 Agent、审批阶段、评分指标或格式硬门禁；内容以支持正确实现、运行和接手为限。

<a id="section-7-2"></a>

### 7.2 规划与脚手架

规划输出包含用户需要的功能、关键接口和必要技术限制。文件蓝图是实现建议，可随业务编辑更新；不预先要求所有符号和引用闭合。

`ProjectScaffoldSpec` 仅表达项目标识、包名、入口类、固定 Profile 和本次需要的基础依赖。`ProjectScaffoldService` 复用已有 POM 模板，生成入口、配置、目录、.gitignore 和最小启动测试。Bootstrap 的编译证明骨架可构建，启动测试则在适当时执行；两者不能混称。

使用少量版本化本地模板，不要求每次在线调用 Initializr。只在新工作区生成骨架；业务编辑开始后，不再整模板覆盖。允许 Agent 在受控依赖来源内提出或实现必要构建调整，不能为了保护脚手架而禁止合理业务依赖。

<a id="section-7-3"></a>

### 7.3 模型可见工具

建议使用以下基础接口；工具数是接口设计结果，不是优化验收目标：

```text
bash(command, cwd, timeout)
apply_patch(patch)
submit_checkpoint(summary, scope = "progress")
report_blocker(reason, kind = "task_blocked")
```

bash 负责搜索、读取、组合命令与局部自诊断。apply_patch 表达源码改动，平台负责路径边界、匹配与实际写入结果。允许完整 Bash 意味着它也能写文件，工作区状态不能只跟踪 patch。

submit_checkpoint 初期就可作为正式验证入口，无需先实现 MilestoneGraph 或 sealed Manifest。第一版以整个当前项目的编译和全量已有测试为主，返回实际结果，不建设按任务自动选择局部检查的机制。后续可选 milestoneId 用于关联任务进度，不用于缩小正式验证范围。

scope 取 progress 或 final，主要区别是是否请求完成交付，而不是选择两套局部测试范围。progress 对整个当前项目执行编译和全量已有测试，结果返回后继续开发；通过只表示当前代码通过这些检查，不表示所有业务已实现。final 在此基础上执行项目既定的整体收尾验收，未通过则继续修复，通过才结束开发循环，不因此新增验收指标。普通文本完成声明不结束任务。kind 取 task_blocked 或 planning_conflict，其处理分别为未完成停止与[第 7.1.4 节](#section-7-1-4)的定向规划交接；新增参数属于目标协议，当前代码尚未实现。

验证响应至少包含代码版本、检查范围、各项状态、真实命令/退出码、关键失败和日志位置。区分“通过”“失败”“未执行或被环境阻塞”，空结果不能算通过；并给出是否允许结束项目的结果。模型不能自行减少检查范围或设置该结果。

Agent 可直接提交 checkpoint 获得编译测试反馈，不要求先自行运行相同命令。首版正式结果只来自平台验证入口，Bash 自诊断输出不直接登记为正式通过。平台在相同源码、配置和检查范围内可复用自身已有结果；状态或环境相关测试无可靠复用条件时重跑，不先建设通用验证缓存。

工具结果保留命令、exit code、耗时与有界输出，完整日志另存。长命令需能超时终止并清理相关进程，不能让后台写入与下一次编辑或冻结验证重叠。

<a id="section-7-4"></a>

### 7.4 上下文与会话

保留简洁需求、当前目标、相关代码、重要实现决策与最近失败。不在每次任务中重复整个架构、批次、契约与文件职责。

按 token 使用量和模型窗口决定压缩，留出输出与工具返回空间。60%/80% 可作实验起点，不作为跨模型统一硬标准。完整 assistant/tool 配对必须保留，压缩失败不得用空摘要替换有效历史。

按[第 7.1 节](#section-7-1)使用统一开发角色连续实现与测试，避免每种工作都重新开启失去上下文的会话。复杂变更才实验开发环节的 Planner/Editor 分离；需要拆任务时，将相关决策和已验证行为传给后续任务。

<a id="section-7-5"></a>

### 7.5 能力里程碑和轻量 checkpoint

按用户可观察的完整能力划分，例如投票项目：

```text
可构建骨架 -> 创建并查询投票 -> 投票与防重复 -> 结果展示和必要页面 -> 最终回归
```

每个能力可同时涉及数据、服务、接口、页面与局部测试。无需固定经过 Domain/Persistence、API、Frontend 三个技术层阶段；纯 REST 项目也无需前端里程碑。

首版任务记录包含 id、目标、状态、相关验证和工作版本即可。完成状态需要对应验证过的代码版本；后续任务修改公共代码时，重跑相关回归。允许合并或细分内部任务，但不能借此删除 required 功能。

保存最近接受的源码 checkpoint 和当前候选，足以支持回滚。跨 run 恢复、复用和全部事件重放留待实际需求出现；原始 JSONL 继续保留。

<a id="section-7-6"></a>

### 7.6 验证与修复

第一版沿用全项目验证思路：开发过程中在一组连贯修改完成后，编译整个当前项目并运行全量已有测试；编译失败时先返回编译错误，修复后再继续测试。这里的“全量”指当前项目的源码和已有测试，不是要求每次提交都已经实现所有业务，也不是每次加入所有可用的检查工具。初始 Bootstrap 仍按脚手架编译处理；尚无业务测试时如实记录，不能把测试缺失当成业务通过。

progress 用于获得反馈和发现跨文件回归，final 用于请求整体交付并执行既定最终验收，包括已有的项目契约等检查。未来功能尚未实现时，progress 不因为完整契约中存在该功能就强制要求立即交付；当前实际编译或测试失败仍返回开发者处理。全项目验证通过与项目需求全部完成保持区分。

Agent 可以通过 Bash 运行单个测试或局部命令快速定位问题，这属于自诊断，不改变正式全量验证策略。验证放在连贯修改之后，不要求每写一个文件就跑一遍，也不要求先自行全量测试再提交 checkpoint 重跑。只有实际耗时已明显拖累开发时，再评估针对性测试选择。

基准验收维护在平台控制的位置；Agent 可编写开发测试，但不能用改写基准测试或修改测试执行配置制造通过。公开全部要求和接口约定，保留具体隐藏数据与测试实现。

首版反馈沿用真实命令、退出码、关键日志，加上相关文件和最近改动。后续再为高频编译/测试错误提取稳定诊断；行号应主要作定位信息，不能因移动几行就判成全新根因。

已通过的明确行为被破坏属于回归；新暴露错误或同数量不同错误需结合内容判断。在全局预算内允许有限中间尝试，停止时保留当前现场和最后可验证候选。

<a id="section-7-7"></a>

### 7.7 模型调用和预算

规划使用正确角色消息与输出结构，工具循环维持真实 assistant/tool 记录。对限流和临时连接错误做有限重试；模型请求重试与工具副作用重试分开，不盲目重复已执行写操作。

优先记录总费用、输入/输出 token、轮次、工具耗时和验证次数，并设置合理全局额度。按任务规模分配开发与收尾预算；引入多个里程碑后不能给每个里程碑无限复制额度。

历史四类会话使用的原有轮次上限可作为旧基线，但不作为目标角色设计的不变量。费用上限不等于每次都消耗相同 token；模型实验分别比较质量与成本，避免把“相同费用”和“相同 token”混为一个约束。

<a id="section-7-8"></a>

### 7.8 Windows 持久化和磁盘真相

```text
Windows: ai_generated_projects/<project_run_id>
                     ⇅ 当前项目读写绑定挂载
Container: /workspace
```

平台先在 Windows 创建项目，再将该目录挂载给候选容器。Bash 在 /workspace 修改的文件立即反映到 Windows，不需要任务结束后 copy-back；删除容器不会删除宿主代码，也不会撤销已发生的删除或修改。

候选代码以磁盘为准，WorkflowData.codes 作为兼容现有服务的派生缓存，在需要时重新加载。Bash 与 patch 写入串行；验证前停止在途写入并确定源码版本。源码快照排除 target、日志与缓存，避免构建噪声扩大扫描和存储成本。

宿主执行 patch 时也必须检查实际目标位于项目根目录内；容器隔离不能代替宿主文件操作的路径约束。正式验收使用不会被 Agent 同时修改的候选版本，回滚由源码 checkpoint 实现。

<a id="section-7-9"></a>

### 7.9 依赖和缓存：先让受控构建可靠

固定当前 Java/Spring Boot/Maven Profile、基础依赖和可信仓库来源，优先使用一份 E 盘共享 Maven 缓存，例如 `.studio-cache/maven/repository`。不为每个项目复制完整 .m2，也不默认挂载用户个人配置和凭据。

依赖由 Maven 解析，平台负责触发预取或在缺依赖时补取，无需自行实现 Maven 依赖图解析器。预取应覆盖实际会执行的构建与测试命令；最小编译成功不能证明测试插件及运行依赖已齐全。

第一轮可先只支持常用依赖组合与配置化版本策略。模型新增依赖经允许来源解析和真实构建验证；不要求所有业务能力都先进入庞大 DependencyCatalog。不存在的坐标或不兼容版本反馈给代码/规划修正，网络故障和缓存故障作为环境问题处理。

Agent 对缓存的写入边界需要实际测试。可先尝试平台预取、候选离线只读使用；如果当前 Maven 工作流需要元数据写入，再验证只读基础缓存加少量可丢弃写入层，或经受控仓库获取的替代方案。不能未经测试就承诺完全只读一定可行，也不能因首次缺依赖就让模型反复改源码。

缓存维护首轮只需避免整仓复制、观察占用和在必要时清理无用版本。完整单写者服务、cache manifest、校验重建和自动淘汰不作为阶段一前置条件。镜像、Maven 缓存、项目 target 和源码应区分占用；历史个人 .m2 约 2.76 GiB 的测量仅作背景，不决定新的硬配额。

<a id="section-7-10"></a>

### 7.10 Hardened SandboxRunner

开放通用 Bash 时同时交付必要隔离：只挂载当前项目、无 Docker socket 和宿主凭据、使用固定可信镜像、非 root、合理资源与 PID 限制、取消和超时清理。按镜像验证只读根文件系统、tmpfs、cap-drop 和 no-new-privileges 的组合。

候选容器默认断网，需要依赖时由平台受控预取或受限来源访问解决。完整 Bash 的边界依赖容器、挂载与网络，而非命令前缀白名单。容器隔离是降低宿主风险的工程边界，不将其表述为绝对安全保证。

持久容器减少反复启动开销，每次命令仍明确 cwd 和环境，不依赖上一次 shell 的 cd/export。镜像预装实际使用的 Bash 和搜索工具；若实际使用 sh，接口和提示也应如实说明。

这些要求随阶段二的 Shell 一起实现，不拖到最后阶段才补。更复杂的多租户隔离和依赖治理根据部署范围另行评估。

<a id="section-7-11"></a>

### 7.11 其他实现歧义的默认处理

以下是第一版实现选择，用来收敛前文的可选路径；不是新增阶段或门禁。

| 问题 | 第一版安排 |
|---|---|
| 多大项目需要拆任务？ | 默认连续开发，规划可提出能力顺序；有多个可独立验证能力且跨度明显时才启用任务推进，不以固定文件数强制拆分 |
| 没有 milestoneId 如何验证？ | 默认编译整个当前项目并运行全量已有测试，不依赖任务标识选择子集；progress 返回反馈继续开发，final 请求既定整体收尾验收 |
| 声明要完成时额度恰好耗尽？ | 平台仍对已保存候选执行可用的最终验证并如实报告，不再增加模型修复调用；Agent stop reason 与产物验收结果分开记录 |
| 任意需求没有完整独立测试怎么办？ | 报告已验证行为和覆盖缺口；构建通过或模型自检不能据此升级为“全部需求已验证” |
| 新增 Maven 依赖如何触发下载？ | 开发者修改允许范围内的 POM，checkpoint 时平台预检和补取允许来源依赖；非法坐标反馈修复，不额外增加依赖管理 Agent |
| 模板何时覆盖已有文件？ | 只在初始脚手架阶段渲染；业务开始后构建修改作为明确补丁处理，修复和规划调整都不整模板重写 |
| patch 部分成功怎么处理？ | 先校验补丁结构和匹配，再写入；实际发生部分写入时返回具体已应用与失败项，并以磁盘重建状态，不重发全部已成功编辑 |
| 如何冻结待验代码？ | 首版顺序执行工具，等待相关命令及后台写入结束后保存源码快照，在独立验证副本运行检查；结果关联源码与配置版本 |
| 验证副本会不会复制 Maven 仓库？ | 仅复制必要源码和项目配置，复用依赖缓存；target、日志、平台验收资产不从候选目录当作可信结果复制 |
| 回滚和提交如何持久化？ | 首版由平台保存最近接受的源码快照，回滚只恢复当前项目受管源码和配置；不要求模型执行 Git commit，也不建设跨 run 重放 |
| 预算结束后的当前候选和较好候选如何交付？ | 保存最后现场；若恢复到较好版本作为交付，应明确该版本及其验证范围，不能把另一个候选的绿色结果附到它上面 |

持续后台服务如页面预览由平台跟踪并在验证、快照或结束时停止，不允许遗留进程继续写工作区。源码快照为版本一致性服务，不因此引入每条工具调用都复制整项目的策略。

## 十一、哪些可移植，哪些暂缓

可优先按 Java 实现参考的机制包括：简洁 Agent/Model/Environment 边界、多文件 patch 表达、编辑失败反馈、有界工具输出、完整轮次压缩、实际验证结果和持续轨迹记录。

需要结合本项目设计的机制包括：绿地脚手架、Windows 工作区与容器协作、任意 Bash 写入的状态发现、业务能力拆分、公开接口与外部验收对齐。它们不能因参考项目有相近名字就视为已验证方案。

暂缓完整规划编译器、提前封存全部实现步骤、跨 run 复用、事件重放、全语言诊断路由、完整符号图和自动多模型调度。需要时再引入，不设为第一轮成功的前置条件。

复制参考代码前的来源与许可核对要求见[许可提示](./01-现状诊断与参考依据.md#licenses)。
