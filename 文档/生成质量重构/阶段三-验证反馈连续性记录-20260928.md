## 本轮实现

开发会话现在记录最近一次尚未解决的 Maven、`compile_main`、`run_tests` 或正式 checkpoint 失败及当时的写入版本。压缩摘要会带上提取后的关键错误行，让后续文件读取和补丁不会把待修错误从上下文挤走。后续成功编译或单个测试通过不清除它；全套测试通过或正式 checkpoint 通过后清除。`run_tests` 的定向测试成功也不再将整套测试标记为已通过。压缩发生在预算末段时，摘要还会用当前剩余轮次重建测试、修复和提交 checkpoint 的提醒，避免沿用过期数字。

固定消息序列测试覆盖失败发生后多轮读取再压缩、里程碑交接与提醒被裁掉、局部测试通过仍保留失败、全套测试通过后清除。此改动只保障验证信息连续性，并不自动修改生成源码，也不能保证模型会正确诊断测试失败。

## 开发模型超时的证据与观测补充

继续使用当前 `qwen3.7-flash` 分析上述两次运行，不因开发阶段成本直接切换模型。第一次 60 次调用中 3 次超时，第二次 47 次中 3 次超时，全部精确达到客户端配置的 240 秒；两次成功调用的中位耗时分别约 4.4 秒和 4 秒，最长分别约 91.9 秒和 82 秒。超时既发生在压缩后的末段，也发生在最近一次工具结果仅几千字符之后；这些数据**不足以证明**请求上下文过大或 240 秒仅差少许，也不能排除供应商处理时延、网络传输或模型生成耗时。非流式 HTTP 请求超时后没有输出 token 用量，旧审计也没有逐轮输入规模，无法进一步分解这三个原因。

现为每个开发模型轮次的审计事件加入消息数、消息正文字符数和历史工具参数字符数；成功响应记录耗时及输出工具参数字符数，异常响应记录轮次、耗时和是否超时。这些字段不复制提示正文，也不等于供应商计费 token，但能在下一次运行中比较输入规模与耗时的关系。固定测试覆盖成功和 240 秒失败事件；全量 `mvn -q test` 完成 55 个套件、237 项测试，0 失败、0 错误、5 跳过。当前保留 `coderModel` 的 240 秒配置：若后续超时明显随输入规模增大，先调整上下文；若是长输出相关，再评估输出上限或超时；若输入规模相近却出现离散的 240 秒超时，则先做一次有记录的 360 秒对照，不把增加等待时间当作质量修复。

## 加入逐轮输入规模后的第三次真实运行

再次重放同一保存规划、`blog-system-basic`、`CONTINUOUS`、`qwen3.7-flash`，保持 60 轮／180 工具调用和 240 秒单次超时：[基准报告](../../benchmark-results/benchmark-2026-09-28T11-00-13.218735Z.json)，候选为 `simple-blog-system_20260928_190013`，[逐轮审计](../../studio-run-logs/simple-blog-system_20260928_190013/tool-calls.jsonl)。60 次请求全部成功，没有超时；模型调用合计 324371 毫秒，整个案例约 448 秒，总计 849815 token。第 34、45、56 轮后发生上下文压缩。模型输入正文峰值约 76632 字符，发生在第 56 轮，该轮仍在约 2.1 秒返回；最慢的成功调用是第 34 轮，约 22.2 秒。故本轮没有证据支持“输入接近当前上限必然引起 240 秒超时”；单次成功运行也不足以排除此前的供应商或网络偶发时延。暂不调整模型或超时参数。

外层独立复核的主代码构建通过，但 19 项测试有 3 项失败、1 项错误，完整语义契约因测试失败未执行；平台与独立质量均未通过。具体失配有四类：`ArticleService.searchArticles` 把 `%` 通配符传给 Spring Data 的 `Containing` 查询，关键词搜索返回空结果；两条成功消息测试使用少于 DTO 最短 5 字要求的标题，却预期重定向；列表测试先保存一个没有必填内容的 `Article`，触发数据库非空约束。末轮模型只读取文件，未提交成功的 final checkpoint，开发因轮次上限停止。这些属于生成候选内部实现和测试输入的一致性问题，不能因本次调用无超时而判定质量改进达标。

三次同规划运行的候选测试均未全绿，且各次生成内容与失败组成不同。下一步应围绕通用的“需求约束、实现、测试样本”一致性与末段验证闭环做受控改进，避免为博客接口添加专用改写规则；改进前先利用这份无超时样本检查模型在收到失败反馈后如何分配剩余轮次。

## 中段验证提醒与第四次真实运行

针对第三次运行直到第 48 轮才首次尝试全套测试、末轮仍未提交 checkpoint 的问题，开发会话在总轮次约三分之二处加入一次完整编译与测试提醒，同时要求成功案例的测试数据符合已声明的校验约束、行为测试必须有实际断言。原有末段提醒保留。固定续接测试验证中段提醒只出现一次；这是促使模型更早拿到反馈的通用提示，不替代真实验收，也不保证模型服从。

同一保存规划的第四次 `CONTINUOUS` 博客运行：[基准报告](../../benchmark-results/benchmark-2026-09-28T11-41-35.003983300Z.json)，候选为 `simple-blog-system_20260928_194135`，[逐轮审计](../../studio-run-logs/simple-blog-system_20260928_194135/tool-calls.jsonl)。模型在第 35 轮编译、第 36 轮跑测试，后于第 48、54、58、60 轮重跑测试；第 40 轮中段提醒确实处于这次运行，但首次测试发生在提醒之前，不能把提前测试归因给提醒。60 次模型调用均成功，无超时，开发仍因轮次上限停止且没有成功的 final checkpoint。

最终独立验证的生产代码构建通过，但 Surefire 的测试 JVM 在启动时报告 `OutOfMemoryError: unable to create native thread`，测试没有正常执行。报告原将其归为 `TEST_COMPILE`，原因是 Maven 正常的 `testCompile` 阶段文字被当成错误信号；现把这一明确的系统线程错误优先归为 `ENVIRONMENT`，避免引导模型修改测试源码来修复资源故障。此分类修复发生在第四次报告生成之后，不回写原始报告。

用同一候选在 Docker 中保留 1 GiB 内存和 128 个进程额度，并设置 `JAVA_TOOL_OPTIONS=-XX:ActiveProcessorCount=2` 后，测试 JVM 正常运行，14 项测试全部执行且全部失败。失败集中在生成的 `ApplicationContextTest.setUp`：它对固定 `/articles/1/delete` 断言 404，但实际返回 200，导致所有测试在准备阶段失败。2026-09-30 复核 Surefire XML 后纠正原归因：日志明确记录 `ArticleNotFoundException` 和 `error/404` 视图；生成的 `GlobalExceptionHandler` 没有设置 HTTP 404 状态，不能将 200 解释成数据库已有文章。固定 ID 与不可靠的测试清理仍是独立缺陷，14 项失败也不能视为 14 个业务行为已经受检。这个复核确认了原报告的资源错误掩盖着生成实现及测试准备问题；一次复核不能证明处理器限制能消除所有环境波动。平台的断网开发及正式验证容器现统一设置该 JVM 选项，生成提示也明确要求测试使用实际持久化或 HTTP 返回的 ID，不假定自增 ID 固定从 1 开始。上述平台修改仍须用后续独立样本验证质量收益。

本轮平台代码在追加线程错误分类和容器 JVM 设置后执行 `mvn -q test`：55 个套件、239 项测试，0 失败、0 错误、5 跳过；`git diff --check` 无空白错误。第四次真实运行发生在这两项追加修复之前，不能把旧报告解释为新设置下的验收结果。
