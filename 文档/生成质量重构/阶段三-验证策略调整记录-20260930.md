## 本轮问题归因和后续边界

生成候选第一次执行测试得到 15 项、4 失败、3 错误，涉及请求 JSON 序列化、响应 DTO 反序列化，导致创建和后续操作连带失败。修复时模型生成的补丁又把完整新类插入旧类之前，留下重复声明；随后还出现给 `final` 字段添加 setter 的编译错误。审计中的补丁确实缺少删除旧类的行，不能把它归为文件并发修改。模型最终用当前文件和编译反馈修复这些问题；JSON 修复后剩余 1 项失败是集成测试共享内存仓储造成的状态污染，最终通过每项测试前清理数据解决，业务断言保持有效。

这些问题发生于 DTO、编辑协议和测试生命周期，具有跨 Spring Boot 项目的适用性；本次没有向平台加入任务 API 业务规则。后续优先用本轮固定补丁和失败日志评估编辑反馈、验证时机及测试隔离提示，避免针对任务名称增加规则。需要区分补丁格式合法、工具成功写入和代码正确；检查是否要拒绝不完整 unified diff 时，也应考虑现有合法补丁，不能一律用不可靠的模型行数制造额外失败。

两次规划调用分别耗时约 134 秒和 243 秒，合计约 6 分 17 秒；开发中的超时单次耗时 240 秒。超时前模型输入正文 33,030 字符、历史工具参数 34,026 字符，重试前没有压缩或重新规划，重试迅速返回，因此本次不能将超时确定归因于上下文过大。第 21 轮发生一次正常压缩，消息由 42 条变为 9 条，后续仍完成验证；该案例只有一个任务，不能验证多任务交接的完整连续性。

本轮错误类型持续变化或减少，未触发新加的重复失败诊断提示或停滞停止。真实运行证明当前链路能够修复并完成另一类简单项目，并验证了一次超时续跑；新提示的消息交付和停止规则仍由固定测试证明，不能宣称真实收益已被本例证实。

### 实际暴露的问题与修复

第一组新说明的第 3 轮补丁已经包含删除重复旧类的行，但省略 `*** Begin Patch`，末尾标记前多一个空格，正文空白上下文行也未保留前缀。解析器将其当作 unified diff 并拒绝，反馈只说缺少 unified diff 文件头；模型随后改成错误的空行删除，再重复原补丁，全部没有写入。仅提供格式说明不足以稳定消除这类协议差异。

本次因此增加确定性兼容：只有明确以原生 Add / Update / Delete 文件操作开始的片段，才补齐外围标记；Update 内无前缀的空行按空白上下文处理，仍必须与磁盘空行精确匹配。不会自动猜测应删除的类、放宽路径或做模糊替换，多文件操作仍全部预检。无法识别的格式错误反馈明确区分原生文件操作与 unified diff 的文件头，避免模型只在错误格式之间切换。
