# 阶段三实施记录（2026-09-26）

## 已实现

主工作流把业务切片与生成计划统一为同一顺序，移除了主链中独立的技术层 BatchPlanning。规划器修正了把“展示／删除关联评论”误判为“提交评论”的情形，并把服务端页面、布局及共享错误处理归入业务任务。过大的资源 CRUD 在有明确接口边界时再细分为“创建与查询”和“修改及附加动作”；简单项目继续使用单任务开发协议。开发 Agent 在同一会话、同一模型与工具预算内逐项提交 `progress` checkpoint。只有当前能力的构建、全量已有测试、当前及此前能力契约均通过，才记录接受状态、受检源码哈希、快照和报告路径；通过后工具反馈带上下一个任务的验收条件与契约，全部能力接受后才允许 `final`。无工具回复时也提醒模型先提交当前任务的 `progress`。

多任务提示只展开当前任务的契约和验收条件，未来任务只列名称；要求先完成当前 `progress` 再实现后续功能。原始大切片的文件清单可能包含未来能力，因此不再作为“当前文件建议”注入模型；完整蓝图仍保留在规划资料中。单任务项目通过 `final` 后直接记录已接受的源码版本，不增加一次 `progress` 验证。

当前细分是保守的启发式规则，不是项目类型白名单或质量保证：只有同一任务中“创建／查询”和“修改／删除等后续动作”各至少有 2 个明确接口、且前端调用都能归属到接口时才拆分；边界不清时保留原任务。评论动作识别优先使用接口路径、请求类型和明确的提交动词，不能仅因页面描述出现“评论”就合并能力。规则依赖常见 HTTP 路径和规划模型给出的契约，对非典型路由及其他技术形态尚无泛化证据；最终 required 行为仍由完整契约和独立判卷检查。

模型与工具轮次、当前任务和失败原因写入项目的 `.software-studio/development-state.json`。`POST /api/SoftwareStudio/projects/{projectId}/resume` 从该项目已有规划资料、磁盘候选和持久化预算续接开发，不重新规划或发放预算。`restore_checkpoint` 先核验最近接受快照的路径与源码哈希，再备份当前候选并恢复受管源码；备份存放于该项目的 `studio-run-logs/.../rollback-candidates`。交付报告增加各里程碑状态和验证版本。

## 已知限制与下一步

业务任务拆分和续接控制已实现，固定规划下 36 轮和 60 轮运行均未交付完整博客；60 轮样本接受首任务，但成本上升且末尾测试编译失败，全项目质量收益尚未验收。下一步优先改善开发测试的版本适配、错误反馈及临近预算时的验证纪律，再用固定规划做受控复核；不能仅靠加大轮次推断方案有效。`resume` 保留已消耗预算，因此用满上限的项目不会自动获得新轮次。阶段四的错误诊断和候选优化尚未在此阶段完整实现。

案例策略沿用实施路线：短链接与投票足够检查固定接口的基础链路，博客用于观察较大任务的拆分失败；目前不靠临时随机增加一次调用来宣称泛化。若后续多任务路径先取得可接受的结果，再从现有案例集中预先选定不同需求形态的案例，固定需求、模型、预算与判卷方式后扩展比较，并逐案例报告成功率与成本波动。
