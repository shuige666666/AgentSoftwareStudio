## 1 核心结论与适用范围

当前已修复若干真实的平台、协议和环境缺陷，但还没有证据表明复杂项目的完整交付已经稳定、明显改善。下一步应让业务验收反馈更早进入同一开发会话，减少工作上下文中的冗余，并重新验证强制里程碑是否帮助交付。继续沿用 PlanningAgent、DevelopmentAgent、工作区工具和平台验证的主链。

本计划是阶段三的调整，沿用原路线中“按需要引入业务里程碑”的原则。为判断阶段三收益，先补必要的上下文与失败反馈；这不等于阶段四的完整诊断、候选比较与回归方案已经交付。稳定的设计协议仍维护在 `02`，实施路线仍维护在 `03`；实际选定规则后再同步对应正文。

本文定位为阶段三的纠偏与收尾验证计划，覆盖当时主要剩余工作。四步按通过条件完成后进入阶段三收尾；完成开发或得到负面实验结论，不等于质量验收通过。第三步负责作出有限的任务策略决定，不承担将复杂项目或两种策略各自优化到最好；后续共同链路问题另行限定范围，不无限扩入第三步。

优先覆盖当前 Java 17、Spring Boot、Maven 项目。优化依据是信息供给、反馈时机、工具消息和验证事实，不增加博客、短链接等案例专用的业务分支。通用机制可以复用到其他项目，但各类项目的独立行为检查仍需依据其公开需求编写，不能承诺自动推导任意业务的正确性判卷。

## 2 当前不足及证据边界

本节保留计划编写时的诊断，以下“当前”“最新”均指原始分析时点；已实施修复和后续结果以主链对照记录为准。

### 强制里程碑的质量收益尚未证实

最新博客对照中，里程碑组独立 HTTP 检查为 4 通过、10 失败、10 阻塞；连续组为 15 通过、9 失败、0 阻塞，两组都未完整交付。连续组主要剩余问题是非法输入和不存在资源的状态码不符合契约，里程碑组还缺少后续业务能力。

同一保存规划不等于实际输入相同：里程碑组初始目标约 3,978 字符，主要提供当前任务契约与原始需求；连续组约 14,955 字符，还包括 PRD、结构和完整契约。因此，这组结果比较的是两种整体开发策略，不能将差异全部归因于任务顺序或 checkpoint。两组都收到过 400 约定，不能把状态码错误一概解释为契约未提供。

当前实现限制提前开发后续能力，并把全部里程碑接受记录作为 `final` 和外层成功的额外条件。应对这些限制做受控比较；最终目标仍是满足完整需求，接受数量本身不是质量指标。一次对照不足以证明连续开发普遍更好，也不足以立即切换生产默认策略。

### 独立业务反馈到达过晚

基准行为判卷在生成结束后执行，博客本轮 HTTP 检查也在候选冻结后运行，失败没有进入当次 Agent 的修复循环。模型主要依赖自行编写的测试，可能让错误实现与错误断言相互吻合。两组都将部分应为 400／404 的响应当作 200，说明构建和自测通过不能代替公开契约验收。

### 压缩后仍缺少可保证的体积上限

当前压缩保留最近三轮完整消息；大量整文件读取可以让压缩后的输入很快再次增大。连续组第 44、45 轮正文均为 81,632 字符，并连续超时。局部读取能力已补齐，但尚未证明模型实际采用它，也未证明输入体积是此次超时的主因。

上下文窗口上限与适合完成当前工作的输入预算应分别考虑。规划元数据可以经 Bash 只读访问，但缺少清楚、易用的按需读取入口；不能据此说模型完全没有访问途径，也不能为了方便读取而开放元数据写入权限。

### 失败反馈和验证时机仍不充分

连续组生成测试存在不满足最小标题长度的“有效输入”、脆弱的页面 ID 提取；里程碑组出现错误 import、依赖校验错误顺序的断言和错误的 model 属性断言。需要依据契约、Surefire 结果和相关源码区分生产缺陷与测试缺陷，不能统一归为业务实现失败，更不能统一删除断言。

两次主链对照中 Agent 均未调用 `submit_checkpoint`，虽然执行过 Maven 编译和测试。这说明工具可用和提示要求并不能保证模型及时进入可信验证。已有重复失败提醒也未在这两次运行中触发，不能提前记为真实质量收益。

### 超时重试仍重复同一大输入

现有受控重试可以保留进度，但连续组最后两次调用使用相同的大输入。应先检查冗余历史、实际请求耗时和供应商异常，再判断是否延长超时；不能把增加轮次或等待时间作为默认修复，也不能认定所有超时都由上下文造成。

## 3 四步实施与验证

### 第一步：改进上下文和失败反馈，先做固定回放

以已有工具轨迹和失败产物为输入，建立按体积控制的工作上下文。保留当前完整目标、有效契约、当前进度、最近失败及正在编辑的准确文本；旧版本和重复的文件正文优先移出上下文，完整材料仍保存在磁盘并能重新读取。压缩必须保持模型工具调用与工具响应合法配对，不得把过期文件片段作为当前源码。

为规划和验收约定提供清楚的只读获取方式。将 Surefire 中的失败测试、预期与实际结果、最早失败位置以及相关文件整理为可操作反馈；先利用现有结果，不建设覆盖所有语言的复杂根因分类器。在超时后的有限重试前，可以压缩冗余历史，但保留未完成目标、源码版本和全局预算。

验证使用“任务交接后压缩”“连续整文件读取”“测试公共前置步骤失败”“超时后重试”等固定序列。通过条件是输入体积受控、关键事实完整、消息配对正确，且反馈能指向已有证据中的真实问题。减少字符数只能证明上下文机制有效，不能单独证明生成质量提高。本步先不追加完整付费生成。

### 第二步：将独立业务反馈接入同一次修复

复用短链接、投票等已有公开契约检查；对其他案例提供少量按需求编写的检查。检查脚本、预期结果和判卷文件由平台保护，Agent 可以看到失败反馈并修改生成实现与测试，不能修改外部判卷来获得通过。

在形成可验证的修改、长时间没有验证或请求结束时，进入适当的验证；根据候选就绪情况运行构建、相关测试及适用的行为检查，不要求每编辑一个文件就运行全套。反馈绑定源码版本，包含请求条件、预期与实际结果；前置能力缺失时明确标为阻塞。

先从已保存的失败候选进行小预算修复对照，固定模型、起点、总预算和验收口径。看真实行为是否改善、已通过行为是否保持、有效测试是否保留。若最终测试失败来自错误测试输入或断言，应凭契约纠正；不能因它阻碍交付就直接跳过。基准最终验收仍独立执行，未知或未覆盖项如实记录。

### 第三步：比较强制里程碑与建议式推进

本步只判断强制里程碑的额外顺序与接受限制是否值得保留，并决定保留、简化或撤回。无需先使两组都达到很好的生成效果，也不要求两组都能编辑或完整成功；某组因自身控制限制停住同样是结果。当前博客两组均无编辑，是有效负面证据，但对任务完成、验证及交接的作用区分有限，不能据此认定两种策略等效。

两组提供相同的完整需求和契约，允许按需读取相同规划材料，保持共享起点、工具、模型、全局预算和最终验收一致。共同运行时、上下文、补丁与反馈问题可以统一修复，比较前冻结共同版本。分别改变策略提示、任务粒度或验证节奏时，应明确改为比较整体方案，不能将全部差异归因于任务控制方式。

主要对照使用一个规模有限、包含两三个关联能力的案例，观察跨任务修改、验证和交接。共享起点已有能力与有效测试通过，尚未实现的需求仍由独立验收检查；不得删改正确断言或降低公开契约来制造绿色起点。接口与判卷在运行前固定，可沿用任务管理 API 等已有案例类型。现有失败博客保留为复杂场景的压力与负面证据，暂不反复重跑。

实验变体将里程碑用于建议和进度记录，允许合理合并、调整顺序、完成共享代码及发起最终验证。完整需求验收仍必须满足；没有逐项接受记录本身不再作为实验变体的交付失败条件。保留与源码版本绑定的 checkpoint 和续接事实，不能把未验证的进度标为接受。

观察完整交付、独立行为覆盖、已有能力回归、源码质量、耗时和用量，而非只看接受数量。未完整成功时，有依据的功能覆盖差异或退化也可参与判断，不必等待两组全部成功。

| 有限比较结果 | 第三步收尾决定 |
| --- | --- |
| 一种策略有明确改善，复核后仍保持 | 选择该策略，记录适用范围、回归情况和剩余限制 |
| 两者接近或优势不稳定 | 不宣称质量优势，依据复杂度、自由度和开销选择较简单的规则 |
| 两者仍无有效编辑或无行为改善 | 记录收益未证实，结束本轮策略比较；共同链路问题另行处理 |

强制控制作为额外限制，应有帮助交付的证据，不能因为先实现就自动视为正确默认。有限比较没有支持其收益且必要回归检查未见明确退化时，优先考虑让里程碑承担建议与进度记录职责，将强制推进保留为可选；完整需求与最终验收继续执行。这是工程取舍，不包装成已证明建议式普遍质量更高。本次有限对照已据此将新项目默认改为 ADVISORY；旧项目续接沿用保存策略，缺少策略的旧状态仍按 ORDERED 解释。具体设计同步 `02`。

### 第四步：在初步改善后验证稳定性与适用范围

前三步产生明确效果后，少量重复运行受影响案例，并轮换任务管理 API、投票或计算器等不同案例。轮换用于发现新边界，不能将不同案例、不同模型的单次成功混成稳定收益。现阶段不直接铺开全部案例的多轮矩阵。

同时核对生成源码的功能完整性、边界处理、跨文件一致性及与项目规模相称的可维护性。平台固定测试通过、日志更清楚、token 更少均是辅助证据。阶段三收尾需要有可重复的真实交付改善、简单案例没有明显无用开销，并明确剩余限制；仍然无收益时应记录未证实，简化方案，而不是继续增加提示和任务层。

本轮第四步先新增投票 REST API 与便签表单项目，各进行一组强制顺序／建议式续建对照，共四次真实运行。两组分别采用相反的执行顺序；每个分支最多 20 次模型调用／60 次工具调用，模型和生产默认预算不变。先修正共同补丁说明与诊断反馈，再冻结同一编译版本、固定源码、人工规划、契约和外部判卷；有效基线测试必须保留。这里判断不同项目类型下的开发控制效果，不宣称已覆盖规划和脚手架的端到端收益。

每个案例先做一组并保留所有失败产物。仅在结果有明确差异且需要确认随机性时，考虑额外重复一组；本轮最多六次，不因发现新问题无限扩大。先记录跨案例结论与剩余限制，再决定是否继续保留强制顺序可选模式。单个案例成功、平台测试通过或轮次较少均不能代替完整功能与独立验收。

本轮已完成上述四次运行，不使用额外两次额度：没有证据支持强制顺序的稳定收益，建议式也出现生成缺陷和判卷漏项。已修复非法 HTML 地址的业务错误分类，并将投票状态序列验收补强；原冻结报告保留，补验只复查保存快照，不调用模型。后续优先做有限的共用编辑可靠性改进，再对默认链运行少量端到端验收；当前不以继续比较两种模式作为收尾前提。结果与限制见主链对照记录“跨案例结果与处理”。
## 4 成本与停止条件

每项实验在运行前记录改动、预期解决的问题、每组模型／工具预算和通过条件。预算依据有限任务与已有轨迹确定，两组一致，运行中不提高；不默认提高生产预算。固定回放优先，比较不以全项目质量已达标为前置条件。

从本次 2026-10-01 范围修订起，第三步总计最多新增两组配对实验，共四次运行，已有实验仍保留为证据。先做一组，出现可解释的差异时再用第二组核实；若两组在第一组都停在编辑之前且无法解释差异，直接记录未证实并收尾，不为凑次数重复。预算用尽、结果接近或持续无收益时，按第三步表格作出决定，不追加第三组寻找偶然成功。

比较前最多安排一批已确定的共同问题修复；实验期间若发现使比较失效的确定性平台缺陷，可以修复，但重新运行也计入上述四次上限。发现新问题、更换假设、修改提示或模型均不重置本次总额度。超过范围的问题进入后续共同改进清单，不以继续优化两种策略为理由扩大第三步。

模型调整与平台变更分别记录；本计划不要求改动用户当前模型配置，也不默认提高生产预算。真实费用无法获取时保持未知，不根据 token 推算账单。保留失败产物和负面结果，以完整交付、独立业务结果和源码质量判断收益。

实施记录补充到各次验证记录中，不为每次局部修复新建一份设计。实际改变设计协议时同步 `02`，改变阶段安排或收尾标准时同步 `03`，实验事实保留原日期和执行条件。
