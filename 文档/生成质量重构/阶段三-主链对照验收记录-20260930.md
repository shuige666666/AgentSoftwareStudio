## 独立 HTTP 判卷与源码核对

[共用判卷脚本](../../studio-run-logs/phase3-main-comparison-20260930/blog-http-smoke.ps1)依据同一保存契约编写，不导入生成的 DTO、测试或实现。候选冻结后只读挂载，以同一 Java 17/Maven 镜像、独立临时工作目录和新应用状态运行；结果与源码 hash 绑定。覆盖创建、列表、详情、编辑、修改、评论、搜索、非法表单、不存在文章及删除。服务运行日志保存，两个验收容器均移除。

判卷在第一次执行时发现 Spring 重定向含 `;jsessionid`，最初严格的路径结尾比较误判；已规范化该路由附加值。功能缺失导致的 404、未修改后的搜索、未删除后的空结果均按依赖标为阻塞，不能算业务通过。修正后重跑同一里程碑冻结副本，连续组使用相同脚本。此为判卷修正，没有重新生成候选。

里程碑候选仅实现创建、列表与搜索，详情、编辑、修改、删除、评论缺失。有效创建成功，但非法创建返回 200，违反保存契约的 400。后续能力缺失意味着本组没有足够证据验证缺失资源或删除效果。

连续候选文章发布、查询、编辑、修改、评论及删除列表记录形成可用闭环。九项失败均涉及 HTTP 状态：非法创建、修改、评论返回 200；五个不存在资源接口返回 200；删除后详情也返回 200。异常处理器虽然返回 `error/404` 模板，但没有设置 404 状态，不能把模板名当响应码。删除后列表不再包含文章，说明删除行为有效，失败的删除后详情检查主要是状态契约不符。

连续组生成测试还存在与业务无关的失败：有些“有效”标题少于契约要求的五个字符；从页面中查找首个 `/articles/` 再截取到 `)` 的方式不能可靠提取渲染后的文章 ID。评论等测试因此调用了错误路径。独立 HTTP 脚本用实际详情链接中的数字 ID，能确认评论闭环；不能把这几项生成测试失败直接归结为评论实现缺失。

## 确认的问题及本轮后续修复

### 1. 登录 shell 丢失 Java PATH（已修复）

里程碑第 27 轮测试编译失败的实际原因是将 `DirtiesContext` 导入错误包。随后第 30–43 轮多次搜索默认 Maven 仓库和诊断工具。平台仓库实际在 `/usr/share/maven/ref/repository`，但模型搜索 `~/.m2`；`java`、`jar`、Python 命令又不可用，进一步浪费轮次。这些工具问题没有造成错误 import，错误 import 也不能解释平台为何丢失 Java 命令。

在同一真实容器只读复现：`bash -lc` 的 PATH 不含 `/usr/local/openjdk-17/bin`，找不到 `java` / `jar`，但 `mvn` 仍能通过 JAVA_HOME 启动；`bash -c` 保留镜像 PATH，可以找到两者。执行改为非登录 shell，仍保留 `pipefail`、非 root、断网、只读根文件系统、候选与元数据路径保护。Bash 工具说明给出准确依赖仓库位置以及不预装 Python / unzip 的事实，避免猜测环境。

真实 Docker smoke 已验证 Java / jar 可执行、Maven 编译、管道失败退出码、候选读写和元数据不可写。没有增加模型调用，也没有修改真实生成候选。

### 2. 最近工具消息使压缩后输入仍很大（增加局部读取，效果未验证）

连续组第 40 轮压缩后，第 41 轮正文为 41,473 字符，接着读取文件使第 44、45 轮达到 81,632 字符，随后两轮均超时。第 35–37 轮也连续压缩，但保留最近三轮完整工具响应，模型第 38 轮输入仍接近 8 万字符。确定的是压缩后并没有可保证的体积上限；超时是否由体积造成仍未证明，供应商负载可能有影响。

`read_files` 现在支持可选 `startLine` / `endLine`，从一开始、包含结束行；默认保持整文件读取。工具说明建议先搜索再局部读取，明确片段不能覆盖完整文件。返回哈希始终对应完整磁盘内容，局部正文保留 CRLF，继续支持准确替换和哈希保护。新增固定测试覆盖片段与完整哈希一致、精确编辑、原整文件读取兼容和错误范围反馈。

这只补足平台能力，尚未证明模型实际采用它或降低了超时，不能将“减少最近三轮大响应”记为已解决。后续应先用现有工具轨迹做压缩体积和消息配对的固定回放，再决定是否调整历史读取保留策略；不直接增加轮次或超时，不截断关键错误和正在编辑的准确文本。

### 3. 测试与保存契约一致性仍不足（未解决）

两组都把表单校验失败当 200；连续组异常页没有 404 状态，生成测试又混入错误输入与脆弱页面 ID 提取。里程碑组测试对约束错误采用单一顺序断言，以及错误的 `articleRequest.title` model 属性断言。这些问题可发生于多数 Spring MVC 项目，不需要加入博客业务关键词规则。

本轮没有手工修好生成源码后宣布生成成功，也没有降低契约、删除有效断言或追加博客提示。后续使用固定产物分别复现测试缺陷与真实状态码缺陷，检查当前任务输入和验收反馈是否准确呈现原契约，再决定最小通用修复；不要重复完整生成寻找偶然成功。
