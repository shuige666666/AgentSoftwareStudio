## 1. 交付目标

本轮工作的目标不是要求 LLM 首次生成就一次成功，而是把原来的“整项目批量生成、统一测试、统一 Debugger 修复”改造成可诊断、受预算约束、能够逐步收敛的垂直切片交付工作流。

质量成功不能只看 `platformSuccess`。最终判断需要同时检查构建退出码、测试实际执行数量、失败和错误数、Spring Context 测试、契约门禁、占位源码和生成项目实物。

## 4. 阶段四：垂直切片交付

### 4.1 切片计划

核心模型：

- `Model/Generation/DeliverySlice.java`
- `Model/Generation/SliceDeliveryPlan.java`
- `Service/Generation/SlicePlanningService.java`
- `Service/Workflow/Node/SlicePlanNodeService.java`

当前策略版本：

```text
vertical-slice-v6
```

主要行为：

- 优先使用 Architect 提供的业务 `batchName` 形成切片；
- 技术层名称如 Controller、Service、Repository 会退化合并，避免恢复瀑布式分层交付；
- 同一个 Controller 承载多个业务能力时，相关后端能力会合并；
- 综合静态前端延后到 `frontend-integration`；
- 评论、投票、结果等附属能力依赖父资源能力；
- 当前切片只暴露已交付源码和当前切片蓝图，禁止引用未来类型；
- 蓝图显式声明、只有一个业务切片消费的基础 DTO、Model、Entity 或异常类型，会自动并入消费者切片；
- Controller、Service 等业务组件不会因为依赖闭包被提前拉入。

### 4.2 切片生成、测试与验收

关键节点：

- `BatchGenerationService.generateSlice`
- `TestGenerationNodeService.executeCurrentSlice`
- `PreflightValidationNodeService`
- `PersistenceNodeService.persistCurrentSlice`
- `VerificationNodeService`
- `EvaluationNodeService`
- `SliceAcceptanceNodeService`

每个切片的主流程为：

```text
规划切片
  → 生成当前切片生产文件
  → 生成聚焦验收测试
  → Profile 与确定性门禁
  → 持久化当前切片
  → Docker 构建
  → Docker 测试
  → 契约门禁
  → 验收或定向修复
```

切片只有在技术验证和契约门禁均通过后才会进入 `acceptedSliceIds`。其测试随后进入 `acceptedTestFiles`，作为后续切片不可随意覆盖的回归基线。

### 4.3 测试统计语义

历史报告中的 `acceptedTestFiles` 实际更接近“生成后通过范围过滤的测试次数”，容易在 0 个切片验收时仍显示较大数字。

当前代码已经拆分：

- `generatedTestFiles`：TestWriter 返回的累计测试文件次数；
- `admittedTestFiles`：通过切片范围过滤并进入工作流的累计次数；
- `acceptedTestFiles`：真正属于已验收切片的唯一回归测试文件数量。

新旧报告中的 `acceptedTestFiles` 语义不同，不能直接纵向比较。

## 5. 当前修复预算

配置文件：`Config/RepairBudgetConfig.java`

当前参数：

```java
MAX_PROJECT_LLM_REPAIRS = 8;
EXTRA_REPAIRS_BEYOND_SLICE_COUNT = 2;
MAX_REPAIRS_PER_SLICE = 4;
RESERVED_FOR_FINAL_VERIFICATION = 1;
MAX_REGRESSION_ROLLBACKS_PER_FAILURE = 2;
```

单个项目实际预算不是固定 8 次，而是根据切片数量计算，并受项目上限、单片安全上限和最终验证预留共同限制。

重要语义：

- 首次生成不计入 repair budget；
- Docker 验证和确定性门禁不计入 repair budget；
- 只有真实调用 Developer、TestWriter 或 Debugger 做修复时才消费一次；
- 所有切片共享同一个全局硬预算；
- 首片失败不会因为旧的两次全局额度直接终止整个项目；
- 无变化、重复失败、环境错误和连续候选退化会提前停止无效调用。

## 6. 修复候选事务与停止原因

核心服务：

- `Service/Repair/RepairRegressionGuardService.java`
- `Service/Repair/ProjectRepairService.java`
- `Service/Workspace/WorkspaceService.java`

每次 LLM 修复前会保存源码、验证证据和失败 fingerprint。修复后如果从测试或契约阶段退化到更早的主代码编译、测试编译或测试发现错误，会恢复内存源码和磁盘文件，并删除本轮新增文件。

当前停止原因包括：

- `BUDGET_EXHAUSTED`：全局或单片预算耗尽；
- `NO_CHANGE`：修复没有产生有效文件变化；
- `REPEATED_FAILURE`：同一失败 fingerprint 再次出现；
- `REPEATED_REGRESSION`：同一基线连续两次产生阶段退化候选；
- `ENVIRONMENT`：Docker 或外部环境失败，不应修改源码；
- `ARCHITECTURE`：需要重新规划，不能由末端 Debugger 盲修。

首次候选回滚后会清除普通重复失败计数并继续使用剩余预算；同一基线第二次退化才停止。

## 7. 当前失败所有权和修复路径

主要分流规则：

- `BUILD_PROFILE` → Profile/POM；
- `MAIN_COMPILE` → Developer 或跨文件 Debugger；
- `TEST_COMPILE`、`TEST_DISCOVERY` → TestWriter；
- 普通 `TEST_CODE` → TestWriter；
- Jackson `InvalidDefinitionException`、`Cannot construct instance`、`no Creators` → 生产实现；
- `TEST_ASSERTION` → 根据 404、模板、固定 ID、MockMvc 500 等证据区分测试和实现；
- `CONTRACT` → Debugger，允许修复契约所有者和受约束集成点；
- `ENVIRONMENT`、`ARCHITECTURE` → 停止 LLM 修复。

Jackson 构造异常会从类名精确定位 DTO 或 Model 文件，例如 `Cannot construct instance of com.example.Point` 优先修复 `Point.java`，而不是删除序列化测试或修改外层消息类。

## 8. 修复阶段新增文件边界

默认规则仍是修复现有文件，防止 Debugger 臆造配置和类型。

只有以下新文件允许补建：

- Controller 已明确返回、错误日志明确缺失的 Thymeleaf 模板；
- 契约明确声明且门禁确认缺失的前端 `sourceFile`；
- 当前切片蓝图已经声明、文件位于 `src/main/java`、且确定性契约门禁正在阻断的生产文件。

这不是按 Snake、URL Shortener 等案例 ID 写死，而是基于蓝图、契约、路径和门禁证据判断。

## 9. Spring Context 测试

`ProjectProfileService` 会检查 Spring Boot 项目是否存在 `@SpringBootTest`。

如果已有 Spring Boot Application 入口但缺少 Context 测试，系统会确定性补充：

```java
@SpringBootTest(classes = XxxApplication.class)
class XxxApplicationContextTest {
    @Test
    void contextLoads() {
    }
}
```

该过程：

- 不调用 TestWriter；
- 不消耗 LLM 修复预算；
- 不重写已有业务测试；
- 自动加入当前切片测试范围；
- 切片验收后成为回归基线。

## 10. 测试密度优化

配置文件：`Config/TestGenerationConfig.java`

当前参数：

```java
RECOMMENDED_MIN_TEST_METHODS_PER_SLICE = 6;
RECOMMENDED_MAX_TEST_METHODS_PER_SLICE = 15;
MAX_RISK_BOUNDARY_TESTS_PER_CRITERION = 2;
```

这是首次切片测试的软约束：每条验收标准优先生成一个主路径测试，最多补两个会改变可观察结果的高风险边界测试。行为较少时允许少于 6 个，不为凑数量生成重复用例。

如果 TestWriter 仍返回超过 15 个 `@Test`，控制台会打印 `Test density warning`。系统不会机械截断 Java 文件，因为截断整类可能制造测试编译错误。

测试修复采用双层定向限制：

- Prompt 要求只返回失败日志点名的测试类；
- `ProjectRepairService` 从日志解析已有失败测试文件，拒绝覆盖未被点名的绿色测试。

日志无法定位具体测试类时，才保留原有范围内的测试修复能力。

新报告至少应满足：

- `repairRollbackCount`、`repeatedRegressionStopCount` 和停止原因与实物一致。

### 13.2 Snake 检查

- 首片测试方法是否由 36 降到约 6～15；
- 超过 15 时控制台是否出现 `Test density warning`；
- Jackson 构造错误是否路由为 `IMPLEMENTATION`；

- Mockito 测试错误修复时是否只修改失败测试文件；
- 是否不再把全部 4 次额度都用于 Tests。

### 13.3 URL Shortener 检查

- `UrlMetadataResponse` 是否与唯一消费者进入同一切片；
- `SLICE_FUTURE_TYPE_REFERENCE` 是否消失或减少；
- 重定向是否仍是实际 3xx + Location；
- 不得重新出现重复 Controller mapping；
- 如果仍 `NO_CHANGE`，检查 Debugger 是否返回相同源码或修复结果被范围规则拒绝。

### 13.4 Poll 检查

- 是否自动出现 `XxxApplicationContextTest.java`；
- 是否不再为 `PROFILE_SPRING_CONTEXT_TEST` 消耗 TestWriter 修复；
- Context 测试是否进入当前切片测试选择范围；
- 是否不再出现两次 `TESTS → TEST_COMPILE → rollback`；
- 若 Context 本身启动失败，应路由真实的 `SPRING_CONTEXT`/实现问题，而不是继续补测试。

## 14. 尚未解决或需要继续观察的问题

### 14.1 终态 FailureKind

早期 Snake 在技术测试通过、契约门禁阻塞并停止后，报告曾出现 `finalFailureKind=UNKNOWN`。这不影响独立质量门禁拒绝假成功，但影响报告诊断准确性。当前尚未单独修复，后续应检查 `SoftwareStudioWorkflowService` 生成最终结果时，是否能从 pending failure、verification 或 contract blockers 中稳定推导终态失败类型。

### 14.2 测试密度是软约束

当前不会强行删除超过 15 个测试方法。若连续真实样本仍明显超过上限，应先记录每片最终测试方法数，再决定是否增加结构化 TestPlan 或二次压缩步骤。不要直接用字符串删除 `@Test` 方法。

### 14.3 蓝图 dependsOn 质量

`vertical-slice-v6` 的基础 DTO 合并依赖 Architect 正确填写 `dependsOn`。如果实际 Architect 经常遗漏依赖，需增加基于契约 request/response type 和 Java 类型引用的确定性补全，而不是放宽所有跨切片文件权限。

### 14.4 Blog 仍是边界案例

Blog 文件多、切片多、模板和父子资源契约复杂，适合测试项目边界，不适合在三案例机制尚未验证时频繁运行。

### 14.5 完整基准尚未恢复

只有当 Snake、URL Shortener、Poll 至少一轮不再重复出现本轮三类工作流缺陷，并且简单案例保持稳定，才应恢复完整基准；比较时需保持相同 commit、模型、温度、token、timeout 和预算配置，最好重复三次。
