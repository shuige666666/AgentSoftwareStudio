# SoftwareStudio 生成质量与垂直切片优化全程总结

> 归档说明（2026-09-16）：正文保留原日期、分支和阶段结论，只用于历史复盘，不作为当前开发指令。现行入口见[文档导航](../README.md)；下方可定位的文档引用已随目录迁移更新。

> 文档时间：2026-08-11  
> 覆盖范围：生成质量基准校准、阶段一至三质量门禁、阶段四垂直切片、多轮 Poll/Blog 真实基准分析与修复  
> 当前状态：阶段四仍在真实基准迭代中；截至本文最后一轮，最新代码修复已通过 59 项聚焦回归，但尚未完成下一轮真实 LLM 基准验证。

## 1. 核心结论

这轮优化不是单纯增加 Prompt 规则，而是逐步把 SoftwareStudio 从“全项目瀑布式生成，最后统一猜错并修复”改造成“以垂直业务切片为单位生成、验证、分类和收敛”的工作流。

阶段一至三主要解决“结果是否可信、失败是否可分类、门禁是否可执行”的问题；阶段四主要解决“错误上下文过大、前序偏差持续扩散、修复边界不清和预算随切片膨胀”的问题。整个过程中没有提高 `max_tokens`、超时或全局 LLM 修复次数，而是依靠确定性归一化、结构化验证、正确的失败路由和更小的交付单元提高有效修复率。

截至最新一次真实基准，已经出现了几个明确的正向证据：

- Poll 首次出现 `firstPassAcceptedSlices=1`，说明至少一个切片能够在零 LLM 修复的情况下通过真实编译和测试。
- Blog 缺失 Thymeleaf 模板的问题已经通过契约蓝图补全消失。
- Java 源码整体二次转义问题已经通过确定性归一化消失。
- 固定数据库 ID、错误页面 DOM 断言等测试所有权问题能够路由到 TestWriter，而不是继续扭曲生产实现。
- `NO_CHANGE`、`BUDGET_EXHAUSTED`、失败类型、修复目标和切片验收情况已经可以在报告中区分，不再只有一个模糊的失败结果。

但当前还不能宣布阶段四完成。最新代码刚补上两个关键能力：后续切片安全扩展既有 Controller/Service，以及根据生成源码自动补齐 JPA、H2、Validation、Thymeleaf Profile 依赖。这两项尚待下一轮真实基准确认。

## 2. 优化前的真实问题

### 2.1 平台成功不等于生成质量通过

早期报告主要依赖 `platformSuccess`、`BUILD SUCCESS` 或执行耗时判断结果，存在“流程正常结束，但没有有效源码或测试没有真正运行”的假成功。All-Flash 的历史结果甚至出现 6/6 平台成功，但生成目录只有空 `sources.txt`，没有可编译 Java 文件。

因此后续分析统一采用以下证据链，而不是单看平台布尔值：

```text
报告参数与 Git/工作区指纹
→ 实际生成目录和源码文件
→ Docker/Java 17 编译退出码
→ Surefire 测试数量、失败和错误
→ 独立质量门禁
→ 结构化失败类型与修复目标
```

### 2.2 工作流本质上仍是瀑布式生成

旧流程虽然使用 LangGraph4j，但主链路仍接近：

```text
生成全部生产代码
→ 统一生成全部测试
→ 统一落盘
→ 最终编译和测试
→ 所有错误交给 Debugger
```

这种方式会把前面产生的契约偏差、类型错位、测试误判、工程依赖和模板缺失全部堆到最后。Debugger 既不知道错误属于实现、测试、契约还是环境，也容易连续修改错误文件。

### 2.3 `maxRetries` 的含义容易被误读

原有 `maxRetries=3` 的真实语义是：一次初始生成，加上最多两次 LLM 修复，而不是三次完整生成。阶段四如果把这个值复制给每一个切片，就会让总修复次数随切片数量增长。

因此后续明确区分：

- 初始生成调用；
- 确定性验证次数；
- 真正的 LLM 修复次数；
- 每个切片的修复归属；
- 最终验证是否借用了保留预算。

## 3. 基准与分析方法的校准

优化开始前先固定了基准分析原则：

1. 报告必须记录模型分配、Git dirty 状态和工作区指纹，避免不同代码、温度、模型和参数混在一起比较。
2. `platformSuccess` 和 `independentQualityPassed` 分开统计。
3. 报告保留聚合失败计数，不长期保存大量原始错误细节；具体错误从当轮控制台和生成目录复现。
4. 记录 `finish_reason`、调用失败类别和 JSON/Schema 输出校验，再决定是否调整 token 与超时。
5. Java 17 生成项目以 Docker/目标编译环境为准；本机高版本 JDK 只能用于辅助诊断。

三次匹配的 Qwen 基线共 18 个样本，平台成功为 5/18，独立质量通过为 3/18，并存在 2 个假成功。Poll 和 Blog 在基线中没有稳定独立通过，因此被选为阶段四的持续回归案例。

遥测结果没有发现 `LENGTH`、timeout、HTTP、JSON parse 等系统性问题，所以保留 `max_tokens=8192` 和原有超时，避免用增加成本掩盖工作流缺陷。

## 4. 阶段一至三：可信验证、确定性门禁和失败路由

### 4.1 结构化验证结果

工作流不再只依赖 Maven 输出字符串，而是通过结构化验证结果记录：

- build/test 退出码；
- 编译是否通过；
- 测试是否真正执行；
- tests、failures、errors；
- 主要失败类型；
- 验证耗时和有效证据。

由此可以区分 `MAIN_COMPILE`、`TEST_COMPILE`、`TEST_DISCOVERY`、`TEST_ASSERTION`、`SPRING_CONTEXT`、`BUILD_PROFILE`、`CONTRACT`、`ENVIRONMENT` 等错误，而不是统一写成“生成失败”。

### 4.2 独立质量门禁

新增或强化的确定性门禁包括：

- 主源码和测试源码是否存在；
- 测试是否真正执行并且 failures/errors 均为 0；
- Spring 项目是否包含上下文启动测试；
- 是否存在占位源码；
- package、public type 和路径是否一致；
- 前端请求字段与 DTO 是否一致；
- Controller 路径变量是否真正使用；
- 静态 `index.html` 与 REST `/` 是否冲突；
- Thymeleaf URL、模板和 textarea 是否存在明显风险；
- 前端声明的调用是否有后端端点。

门禁使用稳定 ID 聚合，例如 `FRONTEND_PAYLOAD_FIELDS`、`CONTROLLER_PATH_VARIABLE_USAGE`、`STATIC_INDEX_ROUTE`、`THYMELEAF_TEMPLATE`、`CONTRACT_FRONTEND_CALL`，便于跨报告比较。

### 4.3 Project Profile 和工程模板

Spring Boot 基准统一归一到 Java 17、Spring Boot 3.2.4，并固定基础 POM。Profile 会处理已知不兼容项，例如错误的 Mock Bean 注解、虚构的 `spring-websocket-test`、缺少 starter-test 等。

这一步的目标是让 LLM 主要生成业务代码，而不是每次从零猜 Java 版本、Spring 版本和测试依赖。

### 4.4 Failure Triage

失败不再全部交给 Debugger，而是按所有权分流：

| 失败类型 | 主要修复目标 |
| --- | --- |
| 测试编译、发现、测试代码错误 | TestWriter |
| 生产编译、运行、Spring 上下文、真实契约行为错误 | Developer / Debugger |
| POM 和固定环境兼容问题 | Project Profile |
| 契约和前端语义门禁 | Contract/对应实现 |
| 架构错误 | 停止盲修，重新规划 |
| 环境错误 | 停止修改源码 |

同时增加重复失败指纹和无变化检测：同一失败重复出现，或者 Agent 返回的代码没有实际 diff 时停止，避免继续消耗预算。

### 4.5 Run Journal 和报告溯源

Run Journal 记录验证、修复目标、修改文件、切片归属和停止原因。基准报告增加：

- `failureCounts`；
- `repairTargetCounts`；
- `failedGateCounts`；
- `noChangeStops`、`repeatedFailureStops`；
- Git dirty 和工作区指纹；
- 结构化 verification summary。

阶段一至三本身没有主动增加 LLM 调用；确定性校验和日志会增加少量本地计算，但能减少无效修复。

## 5. 阶段四：垂直切片交付

### 5.1 目标工作流

阶段四将主链路改造成：

```text
PRD / Architecture / Contract
→ 规划垂直业务切片
→ 生成当前切片生产文件
→ 生成当前切片验收测试
→ 前置门禁与持久化
→ 编译、测试当前切片 + 已验收回归测试
→ Failure Triage
   ├─ 测试问题：重写当前切片测试
   ├─ 单文件实现问题：Developer
   ├─ 跨文件实现问题：Debugger
   └─ Profile/环境/架构：专用处理或停止
→ 当前切片验收
→ 下一切片
→ 最终全量验证
```

### 5.2 新增的核心模型与服务

主要新增或重构的代码位于原有 `Model`、`Service`、`Agent` 分类中，没有新建一级业务包：

- `DeliverySlice`、`SliceDeliveryPlan`：描述切片、文件、契约和依赖。
- `RepairBudget`：全局修复预算及每切片使用情况。
- `SliceDeliverySummary`：向基准报告暴露切片执行结果。
- `SlicePlanningService`：把架构蓝图转换成业务切片，并处理依赖排序、Controller 耦合和前端集成片。
- `SliceProductionScopeService`：限制当前切片可见生产类型，检测未来类型引用。
- `SliceTestScopeService`：限制测试只能覆盖当前或已验收能力。
- `SlicePlanNodeService`、`SliceAcceptanceNodeService`：进入切片流程并提交验收结果。
- `ProjectRepairService`：按所有权、文件边界和契约集成点执行修复。

当前策略版本为：

- 切片策略：`vertical-slice-v5`；
- 预算策略：`global-repair-budget-v2`。

### 5.3 全局修复预算

阶段四坚持一个全局硬上限。初始生成不计入修复预算；在 `maxRetries=3` 下，整个项目最多两次 LLM 修复，而不是每片两次。

报告会记录：

- `repairBudgetUsed`；
- `sliceRepairCounts`；
- `finalRepairCount`；
- `finalReserveBorrowed`；
- `budgetExhaustedAt`；
- `repairStoppedAt`、`repairStopReason`。

这使得“后续切片没有预算”和“Agent 无变化主动停止”可以被明确区分。

### 5.4 已验收测试与生产代码边界

已验收切片的测试作为回归基线，后续切片不能重写。最初生产文件也被完全冻结，但真实 Poll 案例证明，Controller 和 Service 往往是多个业务能力共享的集成点。

当前策略调整为：后续切片可以扩展与当前契约路径明确匹配的既有 Controller，以及该 Controller 直接使用的 Service；其他历史文件仍不可修改。扩展后必须同时通过旧切片测试和当前切片测试。

## 7. 真实案例暴露的问题与逐轮修复

### 7.1 未来类型越界与切片顺序

问题表现：首切片引用后续切片的实体、Service 或资源，导致测试还未生成就出现编译错误。

处理：

- 当前切片只暴露已生成文件和当前蓝图；
- 未来能力使用 primitive ID 或当前切片 DTO；
- 检测 `SLICE_FUTURE_TYPE_REFERENCE`；
- 按主体资源、列表/详情、评论/投票、结果、前端集成排序；
- 同一个 Controller 承载多个能力时尽量合并后端切片。

### 7.2 测试提前发明接口或资源

问题表现：TestWriter 根据验收描述发明 `castVote`、`getResults`、固定列表顺序、未来模板或不存在的方法。

处理：TestWriter 必须先在现有代码中确认方法、构造器、DTO 和资源真实存在；测试范围门禁会跳过未来类型、未来资源和已验收测试覆盖。

### 7.3 实现错误和测试错误路由混淆

典型问题包括：

- Mockito 使用方式错误却修改生产实现；
- 模板不存在却重写测试；
- FrontendContractTest 把表单字段要求在列表页；
- 数据库自增实体的测试硬编码 `/1`；
- 契约端点返回 404 却被当成测试断言错误。

处理：

- 测试编译、发现、Mockito 和明确测试假设归 TestWriter；
- 模板解析失败、契约端点 404、Spring 上下文和真实业务断言归实现；
- 检测 `@GeneratedValue + @SpringBootTest + setId(固定值)`，路由回 TestWriter；
- 移除“所有 IntegrationTest expected/but was 都属于测试”的过宽规则。

### 7.4 多文件运行期契约只修第一处

问题表现：Optional、Controller model、异常处理器和模板表达式互相错位，但单文件 Developer 只能修改第一处，下一轮又暴露第二处。

处理：`TEST_ASSERTION`、`SPRING_CONTEXT` 等实现所有权的运行期问题交给可返回多文件结果的 Debugger；编译日志能稳定定位单个生产文件时仍优先 Developer。

### 7.5 DTO 泛型被近似成 Map

Poll 曾出现 `List<Map<String,Object>>` 传给 `List<PollResponseDto.OptionDto>` 的编译错误。

处理：Developer 和 Debugger 将已生成文件视为不可随意改写的 API，必须精确复制参数、返回值、泛型和嵌套 DTO，禁止用 `Map`、`Object` 或裸集合近似替代。

### 7.6 Debugger 臆造 WebConfig

Blog 曾在修复阶段新增 `WebConfig.java`，并调用不存在的 `enableViewResolvers(...)`，把原问题变成新的编译错误。

处理：修复默认只能覆盖已经生成的文件，禁止新增推测配置类。唯一例外是：日志明确指出某个 Thymeleaf View 无法解析，并且已有 Controller 返回该精确 View 名时，可以补充对应模板。

### 7.7 缺少 Thymeleaf 模板

Blog Controller 返回 `article`，但架构没有生成 `article.html`。

处理分为两层：

1. 契约存在 ViewContract 时，`ProjectContractMergeService` 确定性补成模板蓝图并继承 Controller 的切片归属；
2. 契约遗漏但运行日志明确指出模板缺失时，允许 Debugger 精确补充该模板。

后续真实基准中 `THYMELEAF_TEMPLATE` 和模板解析错误已经消失，说明此优化已得到真实验证。

### 7.8 Java 源码整体二次转义

Poll 的 `GlobalExceptionHandler.java` 曾把所有字符串边界写成源码中的 `\"`，Developer 两次返回相同代码，最终 `NO_CHANGE`。

处理：`SourceCodePathService` 增加安全归一化。只有当整份 Java 文件完全不存在正常双引号、却存在转义双引号时，才解除多余转义层；包含正常字符串边界和合法内部转义的代码保持不变。该归一化统一用于生成、Debugger、Developer 和 TestWriter 写回。

下一轮真实基准中该错误已经消失，并推进到 6 个测试实际执行，因此这项优化已得到真实验证。

### 7.9 固定数据库 ID 的脆弱集成测试

Blog 集成测试对 `@GeneratedValue` 实体执行 `setId(1L)`，不清空数据库，并始终请求 `/articles/1`。生产单元测试全部通过，但集成测试读取到错误记录。

处理：TestWriter 禁止为自增实体指定固定 ID；需要清理仓库、保存实体、读取真实生成 ID，再构造请求。Failure Triage 也会通过源码证据识别这一模式。

### 7.10 后续切片无法扩展已验收 Controller

Poll 首切片生成并验收 `PollController`，后续 `poll-results` 切片生成结果 DTO 和验收测试，但无法增加 `/results` 端点，稳定得到 404。

最新处理：允许后续切片扩展当前契约路径匹配的既有 Controller，以及它直接使用的 Service。无关历史文件仍不可修改，已验收测试继续作为回归基线。

该改动已通过聚焦测试，但尚未经过下一轮真实 LLM 基准验证。

### 7.11 固定 Profile 缺少业务依赖

最新 Blog 生成了 JPA Entity、JpaRepository、事务、Validation 和 Thymeleaf 页面，但固定 POM 只有 web/test，造成 57 个级联编译错误。Developer 无法通过修改单个 Java 文件补救，最终 `NO_CHANGE`。

最新处理：Profile 根据已经生成的明确 import、注解和资源路径确定性补充：

- `spring-boot-starter-data-jpa`；
- H2 runtime；
- `spring-boot-starter-validation`；

### 7.14 进展驱动的切片修复预算 v3

连续真实基准证明，旧 `maxRetries=3` 被解释为“初始生成加两次全项目修复”后，不适合严格串行的垂直切片：当前切片未验收时后续切片无法启动，两次修复经常只够依次暴露主代码编译、测试运行和契约门禁中的前两层问题。

最新处理将阶段四预算升级为 `progress-aware-repair-budget-v3`：

- 切片计划生成后，按 `min(MAX_PROJECT_LLM_REPAIRS, plannedSlices + EXTRA_REPAIRS_BEYOND_SLICE_COUNT)` 建立全项目 LLM 修复硬上限；
- 单切片安全上限由 2 提高到 4，允许同一切片从编译错误继续收敛到测试和契约错误；
- 最终验证保留 1 次软预留；当前切片阻塞且无法到达最终验证时仍可借用；
- `NO_CHANGE` 立即停止，相同失败 fingerprint 再次出现时停止，因此提高上限不等于盲目重复调用；
- 基准报告新增 `repairBudgetLimit`、`sliceRepairSafetyLimit` 和 `finalVerificationReserve`，直接记录真实预算与使用情况。

按当前配置，常见预算为：2 个切片最多 4 次、3 个切片最多 5 次、4 个切片最多 6 次、5 个切片最多 7 次、6 个及以上切片最多 8 次。未发生失败或首次通过的切片不会消耗修复额度，确定性 Profile/路径归一化也不计入 LLM 修复。

修复参数集中在 `Config/RepairBudgetConfig.java` 的四个常量：`MAX_PROJECT_LLM_REPAIRS`、`EXTRA_REPAIRS_BEYOND_SLICE_COUNT`、`MAX_REPAIRS_PER_SLICE`、`RESERVED_FOR_FINAL_VERIFICATION`。每个参数均带有中文作用说明；`RepairBudget` 只负责预算计算与消费，切片计划节点通过 `RepairBudget.forSlicePlan(...)` 启用这些参数。

### 7.19 修复候选事务回滚与重复退化停止

四案例复跑报告 `benchmark-2026-08-12T00-48-43.240142300Z.json` 暴露了一个新的修复生命周期冲突：Snake、URL Shortener、Poll、Blog 都发生了一次候选修复回归，回滚后却立即被旧的“相同失败连续出现”规则停止。四个案例均为 0 个切片验收，其中 Snake、Poll、Blog 停在 `TEST_DISCOVERY`，URL Shortener 停在 `TEST_ASSERTION`。报告已经证明回归检测能够发现修复后从较晚阶段退化到编译或测试发现阶段，但当时无法在回滚后继续使用剩余额度。

为此新增了事务式修复候选机制：修复前保存内存源码、验证证据和失败 fingerprint，记录本次候选修改文件；候选验证发生阶段退化时，精确恢复磁盘与内存中的原文件，并删除本轮新增文件。首次回滚会清除旧的重复失败计数并继续使用剩余全局预算；只有同一基线连续产生第二次回归时，才以 `REPEATED_REGRESSION` 停止。报告同步增加 `repairRollbackCount` 和 `repeatedRegressionStopCount`，从而区分“相同原始失败”“候选修复退化”和“预算耗尽”。

### 7.20 Snake 与 Short URL 双案例复跑结论

双案例报告 `benchmark-2026-08-12T02-08-59.649698Z.json` 验证了新的回滚生命周期。URL Shortener 在发生 1 次候选回滚后仍继续使用了剩余预算，最终使用 4/4 次真实修复，以 `NO_CHANGE` 停止；没有再次被错误的 `REPEATED_FAILURE` 提前截断。这说明“回滚后继续修复”的状态机修复已经实际生效。

但两个案例仍未通过独立质量门禁。Snake 使用 13 次 LLM 调用、97424 tokens，构建成功且 2 个浅层测试通过，但 2 个规划切片均未验收，最终仍有 3 个契约阻塞。生成实物只有应用入口、WebSocket 配置和静态页面，没有承接 `/app/command`、`/app/restart` 与 `/topic/game` 的消息 Controller、业务服务或领域实现。它以 `REPEATED_FAILURE` 停止，说明原修复器只能修改已有文件，无法补建架构已声明但首次生成遗漏的生产所有者。

URL Shortener 使用 21 次 LLM 调用、199849 tokens，构建成功，16 个测试中 5 个失败。生产代码同时声明了两个重叠的 `GET /{shortCode}` 路由，并通过抛出 `RuntimeException` 模拟重定向；测试又把重定向错误地断言为 500、用字符串偏移解析 JSON，并对不可控随机碰撞断言固定调用次数。更关键的是，四次修复全部路由到 Tests，确定性的重复路由和重定向契约阻塞没有优先得到生产修复。

### 7.21 架构声明漏文件补建与契约优先修复路由

针对 7.20 暴露的两类通用缺陷，本轮没有按案例 ID 写特殊分支，而是收紧并扩展工作流规则：

- Debugger 只可补建当前切片蓝图精确声明的 `src/main/java` 文件，并且必须有确定性契约门禁正在阻断；未声明配置类或任意应用类型仍会被拒绝；
- 构建通过后，若 `TEST_CODE` 或 `TEST_ASSERTION` 与确定性契约阻塞同时存在，Evaluation 优先把测试症状和门禁证据合并交给契约/生产修复；`TEST_COMPILE` 和 `TEST_DISCOVERY` 仍归测试所有；
- Developer/Debugger 要求重定向返回真实 3xx 与 Location 或合法 MVC redirect，禁止以 RuntimeException 模拟，并要求公开重定向路由与元数据接口使用不重叠的 method/path；
- TestWriter 要求用 ObjectMapper、JsonPath 或 Spring JSON 断言解析响应，禁止手工 substring 偏移；随机生成器不可控时不得断言精确碰撞重试次数，也不得把成功重定向断言为 500。

新增的漏文件准入和契约优先路由测试通过，连同修复、门禁、回滚、工作流终态和报告序列化共 59 个聚焦测试全部通过。本轮未调用真实 LLM，也未运行 Docker，因此是否能让 Snake 补齐消息处理层、让 URL Shortener 将额度从测试改写转向生产契约，仍需下一轮相同双案例验证。

### 7.22 三案例复跑与测试价值优化

三案例报告 `benchmark-2026-08-12T03-42-21.871388300Z.json` 运行 Snake、URL Shortener 和 Poll，三者均未通过独立质量门禁，但进一步缩小了修复所有权问题。全部 57 次 LLM 调用正常结束，没有超时、截断、HTTP、解析或 Schema 错误。

Snake 已由上一轮只有 2 个浅层测试推进到 36 个测试、34 个通过，生产实物包含 Controller、Service、Rules Engine、DTO 和领域模型，契约门禁也已通过。剩余错误分别是 Mockito 无效桩和 Jackson 无法构造只有双参数构造器的 `Point`；后者属于生产模型错误，却因整体分类为 `TEST_CODE` 连续进入 TestWriter，最终使用完 4/4 次修复。URL Shortener 已生成真实 3xx 与 Location 重定向，但首片提前引用未来切片的 `UrlMetadataResponse`，两次实现修复后以 `NO_CHANGE` 停止。Poll 缺少 `@SpringBootTest`，两次整批测试修复都退化为 `TEST_COMPILE`，候选回滚两次并以 `REPEATED_REGRESSION` 正确停止。

据此完成四项通用调整：

- `TEST_CODE` 中出现 Jackson `InvalidDefinitionException`、`Cannot construct instance` 或 `no Creators` 时归生产实现，并从异常中的类名精确定位 DTO/模型文件；
- Developer/Debugger 强制为参与 HTTP/WebSocket 消息的类型提供明确 Jackson 构造方式，并禁止当前切片生成未来契约能力；
- 切片规划策略升级为 `vertical-slice-v6`：仅把蓝图显式声明、只有一个业务切片消费的基础 Java 支持类型并入消费者切片，不提前拉入 Controller 或 Service；
- Spring Boot 入口存在但没有 `@SpringBootTest` 时，由 ProjectProfile 确定性增量生成最小 Context 测试，保留所有已有业务测试，不调用 LLM、不消耗修复预算；该测试会进入当前切片验证范围并在切片验收后成为回归基线。

报告统计也做了语义纠正：`admittedTestFiles` 表示通过范围过滤、被工作流接收的生成测试次数；`acceptedTestFiles` 改为真正属于已验收切片的回归测试文件数。这样不会再出现 0 个切片验收却显示大量 accepted tests 的误导。

以上定向回归 67/67 通过；随后扩大到切片规划、生成范围、契约、Profile、修复、候选回滚、验收、工作流终态和报告序列化的阶段四联动回归，共 101/101 通过。本轮未调用真实 LLM，也未运行 Docker。

### 7.23 首轮测试密度与失败测试定向修复

Snake 单个首片生成 36 个测试方法，其中核心状态和规则测试占 26 个。测试本身发现了真实的 Jackson 反序列化缺陷，但在切片尚未验收时，大量近似边界用例扩大了测试夹具、执行和修复表面积，并使一个 Mockito 无效桩和一个生产序列化问题消耗完 4 次修复预算。因此本轮保留生成测试和回归基线设计，但增加测试密度控制。

新增 `Config/TestGenerationConfig` 集中维护三个参数：首次切片建议 6～15 个测试方法，每条验收标准除主路径外最多补 2 个高风险边界。该上限通过 TestWriter Prompt 约束，并在返回超过 15 个 `@Test` 时写入控制台密度警告；工作流不会机械截断完整 Java 类，避免为限制数量制造测试编译错误。测试数量少于 6 但已覆盖全部可观察行为时也允许继续，不为凑数量制造重复断言。

测试修复同时改为定向模式：Prompt 要求只返回失败日志点名的测试类；`ProjectRepairService` 会从日志解析现有失败测试文件，并拒绝 TestWriter 返回的其他绿色测试修改。只有日志无法定位具体测试类时，才保留原有范围内修复能力。该策略减少整批重写、回归候选和无效 token，但不增加 LLM 调用，也不改变全局修复预算。

测试密度、完整文件保留和失败文件过滤的定向回归共 31/31 通过；随后纳入切片规划、Profile、契约、修复、回滚、验收和报告序列化的阶段四完整联动验证，共 103/103 通过。

## 10. 下一步计划

### 10.1 先复跑 Snake 与 URL Shortener

优先使用相同配置复跑：

```json
["snake-websocket-basic", "url-shortener-basic"]
```

重点观察 Snake 是否实际新增蓝图已声明的消息 Controller/Service，`CONTRACT_FRONTEND_CALL` 是否收敛；URL Shortener 的 `repairTargetCounts` 是否从四次 Tests 改为出现 CONTRACT，以及最终路由是否为不重叠的真实 3xx 重定向。还需确认回滚后仍能继续消耗剩余额度，并检查 `NO_CHANGE`、`REPEATED_FAILURE` 和 `REPEATED_REGRESSION` 是否与最终实物一致。

### 10.2 双案例改善后回归三个简单案例

先运行：

```json
["calculator-web-basic", "task-api-basic", "url-shortener-basic"]
```

下一轮重点检查：

- 报告中的 `budgetPolicyVersion` 是否为 `progress-aware-repair-budget-v3`；
- `repairBudgetLimit` 是否与 `plannedSlices` 和 `RepairBudgetConfig` 中的两个预算参数一致；
- 同一切片从编译错误进入测试或契约错误时，是否能继续修复而不是在两次全局额度后提前停止；
- `NO_CHANGE` 和重复 fingerprint 是否仍能及时阻断无效调用；
- 已验收切片的测试是否持续作为后续回归基线；
- 三个简单案例的主代码、测试和独立质量门禁是否通过。

### 10.3 达到双案例稳定后扩大回归

Poll/Blog 至少连续两轮不再出现同类框架缺陷后，再运行四个重点案例：

```text
snake-game-basic
short-link-system-basic
poll-system-basic
blog-system-basic
```

之后再恢复完整基准集，并在同一 commit、工作区指纹、模型分配、温度、token、timeout 和预算策略下至少重复三次。

### 10.4 优化大切片退化

如果 Blog 继续退化为单个 20 多文件切片，应为技术层 batchName 的 fallback 增加“按业务领域聚类”的确定性规则，而不是简单全部合并。目标是避免恢复瀑布式技术层，同时也避免单片过大。

### 10.5 补充切片计划可观测性

建议在报告中增加聚合、低敏感度的切片计划信息，例如：

- 切片 ID 列表；
- 每片生产文件数和测试文件数；
- 每片首次验证结果；
- 每片最终失败类型；
- 共享/可扩展集成点数量。

这样可以减少每轮依赖控制台重建切片计划，但仍不需要保存完整失败日志。

### 10.6 暂不增加预算和模型参数

当前失败主要来自路由、边界、Profile 和测试假设，不是 token 截断或超时。应先观察首次切片通过率和有效修复率；只有在失败已经正确分类、修复确实产生有效 diff，但两次全局修复仍稳定不足时，才讨论调整预算。

## 11. 可用于项目介绍或面试的总结

这次优化的价值不只是“多写了几个 Prompt”，而是完成了一个可解释的软件生成质量闭环：

1. 用独立门禁揭示平台假成功；
2. 用结构化验证替代字符串猜测；
3. 用 Failure Triage 明确实现、测试、契约、Profile 和环境所有权；
4. 用全局预算约束 Agent 修复成本；
5. 用垂直切片缩小错误上下文，并用已验收测试保护回归；
6. 用真实基准产物持续发现设计缺陷，再通过确定性规则和聚焦回归修复；
7. 明确区分单元测试通过、真实 LLM 基准进展和最终质量结论。

当前最重要的工程成果，是系统已经能够回答“失败发生在哪个切片、属于谁、用了几次真实修复、修改了哪些文件、为什么停止”，并开始出现零修复通过的真实切片。下一阶段目标是让这种局部收敛稳定扩展到完整项目，而不是通过增加模型调用强行提高偶然成功率。
