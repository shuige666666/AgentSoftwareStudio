核心变化可以概括为一句话：以前是“按垂直切片边生成、边门禁、边修复”，现在改成“先生成完整生产项目，再让真实编译和测试驱动连续修复”。

## 一、整体流程调整

原流程把垂直切片当作强执行边界。每个切片都要经历生成、测试、校验、修复、验收，然后才能进入下一片。这种设计流程可靠，但会带来两个问题：

- 项目还不完整时就开始编译和修复，很多错误只是“未来文件尚未生成”，修复器拿不到完整上下文；
- 每个切片重复触发门禁和 Agent，消耗了时间与 Token，却未必改善最终产物。

现在的新流程是：

````mermaid
flowchart LR
    A["需求与架构"] --> B["生成项目契约"]
    B --> C["生成完整生产代码"]
    C --> D["前端一致性审查"]
    D --> E["真实 Docker 编译"]
    E -->|失败| F["生产代码修复循环"]
    F --> E
    E -->|通过| G["统一生成测试"]
    G --> H["真实 Docker 测试"]
    H -->|失败| I["测试/实现修复循环"]
    I --> E
    H -->|通过| J["最终契约检查"]
    J -->|失败| K["契约专项修复"]
    K --> E
    J -->|通过| L["最终成功"]
````

主要涉及以下模块：

- [SoftwareStudioWorkflowService.java (原记录 line 79)](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Workflow/SoftwareStudioWorkflowService.java)
  从原来的 LangGraph 切片循环，改成质量优先的完整项目流程。

- [BatchPlanningService.java (原记录 line 73)](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Generation/BatchPlanningService.java)
  不再按业务 `batchName` 隔离生成，而是按照依赖层生成：DTO/实体 → Repository → Service → Controller → Frontend。这样下游代码生成时能看到已经生成的真实上游接口。

- [PersistenceNodeService.java](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Workflow/Node/PersistenceNodeService.java)
  增加完整项目统一落盘能力，保证 Docker 和修复器面对的是同一份项目状态。

- [DockerSandboxService.java](../../src/main/java/com/core/multiAgentSoftwareStudio/Tool/DockerSandboxService.java)
  增加专门的真实编译命令。Spring/Maven 项目运行：

  ```
  mvn -DskipTests compile
  ```

  编译通过之后才允许生成和运行测试。

垂直切片没有彻底删除，目前仍用于业务规划、上下文说明和报告，但不再控制编译、修复和验收边界。

## 二、修复循环如何设计

核心实现是 [ToolDrivenRepairService.java (原记录 line 96)](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Repair/ToolDrivenRepairService.java)。

它把每次 LLM 修改都视为“候选补丁”，而不是直接认为修复成功。完整循环是：

1. 运行真实编译或测试；
2. 获取命令、退出码和完整错误输出；
3. 将最新错误交给对应修复器；
4. 修复器返回一个或多个完整文件；
5. 写入内存和真实项目目录；
6. 立即重新编译；测试阶段还要重新运行测试；
7. 根据前后两次真实结果决定提交、继续还是回滚。

因此，Agent 说“已经修复”没有任何效力，只有编译器、测试和最终契约结果才能确认修复有效。

## 三、3+1 修复预算

现在整个项目共享 4 次硬额度，但并不是默认执行 4 次。

默认最多连续修复 3 次：

- 第一次修复后有进展，可以继续；
- 第二次仍有进展，可以继续；
- 第三次如果真实验证仍有进展，才开放第 4 次；
- 第三次没有进展，直接停止，不使用第 4 次。

这里的“有进展”不是 Agent 自己声明，而是由 [RepairProgressEvaluator.java](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Repair/RepairProgressEvaluator.java) 根据真实结果判断。

验证阶段大致按照以下顺序衡量：

```
构建配置错误
→ 生产代码编译错误
→ 测试代码编译错误
→ Spring Context/实现错误
→ 测试运行错误
→ 契约错误
→ 全部通过
```

以下情况算有进展：

- 从生产代码编译失败进入测试编译失败；
- 从测试编译失败进入测试运行失败；
- 相同失败类型下，编译器错误数量减少；
- 测试失败数或错误数减少；
- 最终全部通过。

以下情况不算有进展：

- 错误类型没变，错误数量也没减少；
- 修改了文件，但工具结果完全相同；
- 从测试失败退化为生产代码编译失败；
- 新错误处在更早的验证阶段。

## 四、候选事务与最佳检查点

候选修复的事务控制放在 [RepairRegressionGuardService.java](../../src/main/java/com/core/multiAgentSoftwareStudio/Service/Repair/RepairRegressionGuardService.java)。

每次调用修复器前，会保存：

- 当前所有源码；
- 当前验证结果；
- 当前编译和测试输出；
- 当前失败类型；
- 当前质量检查结果；
- 本轮发生变化的文件列表。

修复后：

- 如果真实验证有进展，则提交候选，把它变成新的最佳检查点；
- 如果没有进展或发生退化，则同时恢复内存源码和磁盘文件；
- 回滚后提前停止，避免继续基于更差的代码消耗 Token。

这解决了以前“修复器越修越坏，但后续轮次仍在坏代码上继续修”的问题。

## 五、修复责任拆分

以前大部分失败都会交给一个很长 Prompt 的 `DebuggerAgent`。它同时要理解编译、Spring、测试、契约、前端和文件权限，职责过重。

现在分为三类：

### ImplementationRepairAgent

`src/main/java/com/core/multiAgentSoftwareStudio/Agent/ImplementationRepairAgent.java`（历史路径，当前分支不存在）

负责：

- 生产代码编译失败；
- 跨文件方法签名不一致；
- DTO、Service、Controller 调用不一致；
- Spring Bean、依赖注入和 Context 错误；
- 测试暴露出的真实生产实现错误。

它允许一次返回多个相关生产文件，并要求同时修复定义方和调用方。

### ContractRepairAgent

`src/main/java/com/core/multiAgentSoftwareStudio/Agent/ContractRepairAgent.java`（历史路径，当前分支不存在）

负责：

- HTTP method/path 不一致；
- 请求与响应 DTO 不一致；
- 状态码和重定向错误；
- Controller、Service、异常映射不一致；
- Thymeleaf 模板和前端调用契约问题。

它只在真实编译、测试提供证据后工作，避免凭静态告警盲目调整接口。

### TestWriterAgent 与 DebuggerAgent

测试自己编译失败、测试发现失败或者确定属于测试假设错误时，仍由 `TestWriterAgent` 重写测试。

精简后的 `DebuggerAgent` 只作为无法明确归属时的通用兜底，不再承担所有修复职责。

路由集中在 `src/main/java/com/core/multiAgentSoftwareStudio/Service/Repair/ProjectRepairService.java`（历史路径，当前分支不存在）。

## 六、修复器实际能修改什么

修复器并没有获得任意 Shell 权限。真实工具仍由平台控制：

- 平台运行 Docker 编译和测试；
- 平台提取命令、退出码和错误输出；
- LLM 只返回结构化的完整文件修改；
- 平台校验路径、空文件、修改范围和是否允许新增；
- 平台写入候选文件；
- 平台再次运行真实工具。

这种设计接近 Codex 的“修改—执行—观察—继续修改”模式，但工具执行权掌握在工作流中，不依赖模型主动正确调用工具。

## 七、这次刻意减少了什么

这次没有继续增加新的质量指标，反而移除了主路径中的大量中间切片操作：

- 不再每个切片都生成测试；
- 不再每个切片都运行 Docker；
- 不再每个切片都触发独立修复预算；
- 不再把尚未完整的项目当作失败产物修复；
- 不再依赖 Agent 的完成声明；
- 不会因为改了文件就认为有进展。

最终只有三个关键事实决定成功：

1. 生产代码真实编译通过；
2. 真实测试被发现且全部通过；
3. 最终契约不存在阻断项。

目前这些机制和回滚行为已经通过单测、Spring Context 和真实 Docker 冒烟测试；至于真实生成质量提升多少，还要通过下一轮同案例重复基准来确认。
